# ხარისხის კონტროლის ერთიანი პლატფორმა — მოთხოვნა და რეკომენდაცია IT-სთვის

> ადრესატი: საჯარო რეესტრის ეროვნული სააგენტოს IT სამსახური.
> მომზადდა: 2026-10-20 · კონტაქტი: ლუკა ნუკრაძე, სალომე დავითაშვილი (ხარისხის კონტროლი).
> ტექნიკური აღწერა: [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. რა არის

ვებ-პლატფორმა ერთ სისტემაში აერთიანებს ხარისხის კონტროლის ყველა ნაწილს:
- ოქმების განაწილებას;
- QC შემოწმებას;
- ველის პასუხებს და „არ დათანხმებულებს“;
- სტატისტიკას;
- Pre-QC-ის (ავტომატური წინასწარი შემოწმების) შედეგებს.

ის ცვლის Google ცხრილებსა და დესკტოპ-პროგრამას. იყენებს დაახლოებით 300 თანამშრომელი (ამზომველები, მენეჯერები, კონტროლი), მათ შორის ველიდან ტელეფონით/პლანშეტით. ლოკალური პროტოტიპი მზადაა და რეალურ მონაცემზე მუშაობს.

## 2. ძირითადი პრინციპები

1. **მხოლოდ კითხვა.** პლატფორმა სააგენტოს სისტემებში (REGFIELDALL, REDI, SLR) არაფერს წერს.
2. **საკუთარი ასლი.** საჭირო ველების ასლს პლატფორმა თავის ბაზაში ინახავს და განრიგით ანახლებს (ღამით და საჭიროებისამებრ). ამიტომ წყარო სისტემებს დატვირთვა არ ემატება და დროებით მიუწვდომლობასაც უძლებს.
3. **მინიმალური მონაცემი.** მხოლოდ ის ველები გვჭირდება, რაც სამუშაოს სჭირდება. მაგალითად, განმცხადებლების პირადი ნომრები და ტელეფონები არ გვჭირდება.
4. **მინიმალური უფლება.** თითო წყაროს ცალკე სერვისის ანგარიში, მხოლოდ საჭირო view-ზე და მხოლოდ ჩვენი სერვერიდან.
5. **გადატანადი.** სისტემის ყველა პარამეტრი (ბაზა, დომენი, OAuth, SMTP) კონფიგურაციაშია. სერვერის ან ინფრასტრუქტურის შეცვლა კოდის შეცვლას არ მოითხოვს.

## 3. მონაცემზე წვდომა — რეკომენდაცია თითო წყაროზე

უპირატესობის რიგი: **(ა) read-only view ბაზაში → (ბ) REST API (JSON) → (გ) ღამის ფაილი დაცულ საქაღალდეში (SFTP)**.

| წყარო | რა გვჭირდება | რეკომენდაცია | სათადარიგო | სიხშირე |
|---|---|---|---|---|
| **REGFIELDALL** (საველე ოქმები) | `FLD_PAPER_ID`, `CADCODE`, `MOX_CREATE_DATE`, `FLD_STATUS_NAME`, `OQMI_CREATOR`, `MOXAZ_CREATOR`, `IS_LAST` | (ა) view, ცალკე read-only მომხმარებლით | (გ) ღამის GDB/CSV ექსპორტი (ახლა — `Z:\REGFIELDALL`) | ღამით + მოთხოვნით |
| **სპორადული დათვალიერებები** (ახლა ყოველდღე xlsx მეილით) | `FLD_PAPER_ID`, `CADCODE`, `CREATE_DATE`, `SURVEY_DAY`, `SURVEY_TIME`, `CALL_STATUS`, `ST_NAME`, `TR_NAME`, `USER_REAL_NAME`, `REGNUMBER` — **განმცხადებლების მონაცემის გარეშე** | (ა) view | (გ) ყოველდღიური ფაილი SFTP-ზე (მეილის ნაცვლად) | ყოველ დილით |
| **ოქმის დეტალები** (შემსრულებლები, Pre-QC) | ოქმის ველები; შემსრულებლები სტატუსით „საველე სამუშაოების შესრულებაზე უფლებამოსილი პირი“; დანართების სია | (ბ) API: ოქმი ნომრით → JSON | ოქმის HTML/TXT ექსპორტი | ოქმზე, მოთხოვნით |
| **REDI / SLR / WFS** (Pre-QC შემოწმებები) | ნაკვეთის სტატუსი, რეგისტრაციის მონაცემი, SLR განაცხადები, ფენები | (ბ) read-only API / WFS | (ა) view | მოთხოვნით |
| **Field Group** (გუნდები: ამზომველი → მენეჯერი) | სახელი, გვარი, მენეჯერი, აქტიურობა | შემდეგში — პლატფორმაში ადმინი მართავს | ახლანდელი Google ცხრილი (მხოლოდ კითხვა) | ყოველდღე |

ჩვენი მხრიდან თითო წყაროს ცალკე „კონექტორი“ ექნება, ერთიანი ინტერფეისით. ის აწარმოებს იმპორტის ჟურნალს (რამდენი ჩანაწერი, როდის, შეცდომა), გაიმეორებს მცდელობას და შეცდომაზე შეგვატყობინებს. წყარო სისტემაში ცვლილება არ ხდება.

## 6. Google-ით შესვლა

- **Google Cloud პროექტი** სააგენტოს სახელზე და **OAuth client** (Web application).
- **Redirect URI:** `https://<დომენი>/auth/google/callback`.
- **ვინ შედის:** თანამშრომლები პირადი Gmail-ით (მენეჯერები აგროვებენ სახელს, გვარს და ელფოსტას). თუ სააგენტოს Google Workspace აქვს, შესაძლებელია ერთი დომენით შეზღუდვაც.
- **ჩვენ გვჭირდება:** Client ID და Client Secret (გადმოცემა უსაფრთხო არხით).

## 7. მეილი

- **SMTP relay:** host, port, ავტორიზაცია.
- **გამგზავნის მისამართი:** მაგ. `qc-noreply@napr.gov.ge`, SPF/DKIM-ით, რომ სპამში არ მოხვდეს.
- **მოცულობა:** დღეში ათეულობით შეტყობინება, ძირითადად საველე მენეჯერებთან (დაბრუნებული ხარვეზი, „არ დათანხმებულის“ გადაწყვეტილება).

## 8. შემოთავაზებული თანმიმდევრობა

1. სერვერი, PostgreSQL, დომენი და HTTPS — პილოტისთვის საკმარისია. მონაცემი ჯერ ახლანდელი გზით მოდის.
2. REGFIELDALL-ის view → განაწილება ავტომატურად, ღამის განახლებით.
3. სპორადულის view → ყოველდღიური სია მეილის გარეშე.
4. Google OAuth და SMTP → საწარმოო შესვლა და შეტყობინებები.
5. ოქმის API და REDI/SLR/WFS → Pre-QC რეალურ მონაცემზე.

## 9. კითხვები IT-სთვის

1. სად შეიძლება სერვერის განთავსება და რა OS/ვირტუალიზაცია გაქვთ სტანდარტად?
2. REGFIELDALL-ზე და სპორადულის სიაზე view შესაძლებელია? თუ არა, რომელი ფაილის ფორმატი და რა სიხშირე?
3. არსებობს ოქმის შინაარსის (შემსრულებლები, დანართები) API? რომელ ფორმატში?
4. REDI, SLR და WFS-ზე read-only წვდომა სერვერიდან რა გზით არის შესაძლებელი?
5. გარედან წვდომა — საჯარო HTTPS, თუ მხოლოდ VPN?
6. Google Workspace აქვს სააგენტოს, თუ პირადი Gmail-ები გამოვიყენოთ?
7. SMTP relay და გამგზავნის მისამართი — ვინ გასცემს და როდის?
