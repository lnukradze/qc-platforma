# ა. ზოგადი და მენეჯმენტი

### Q1. 🟢 რა არის ეს სისტემა და რატომ გჭირდებათ?

**🗣 მოკლე პასუხი:** „ეს ხარისხის კონტროლის ერთიანი ვებ-პლატფორმაა. ხუთ ცალკე ინსტრუმენტს ცვლის: Google ცხრილს, მის სკრიპტებს, განაწილების დესკტოპ-პროგრამას, სტატისტიკის პანელს და Pre-QC-ის შედეგებს. ≈ 300 თანამშრომელი ერთ ადგილას იმუშავებს, თავისი როლით. ყოველი ნაბიჯი ისტორიაში ინახება, და წესებს სისტემა იცავს.“

**🔧 ტექნიკური ახსნა:** FastAPI-ზე (Python) აგებული მონოლითური ვებ-აპლიკაციაა, სერვერზე აწყობილი HTML-ით (Jinja2 + HTMX), რელაციური ბაზით (SQLAlchemy; პროტოტიპში SQLite, საწარმოოში PostgreSQL), RBAC-ით და საკუთრების ფილტრებით. სამუშაო პროცესი state machine-ია: 7 მდგომარეობა, append-only ისტორია. წყარო სისტემებს მხოლოდ კითხულობს.

**💬 მარტივად რომ გავიგოთ:** დღეს ოქმი რამდენიმე პროგრამასა და ცხრილს შორის „დადის“, და ყველაფერს ადამიანები ამოწმებენ. ახალ სისტემაში ოქმი ერთ ადგილას ცხოვრობს, ზუსტად ჩანს, ვისთანაა, და არასწორი ნაბიჯი შეუძლებელია.

**📌 ჩვენი პროექტიდან:** ✅ ლოკალური პროტოტიპი v0.2.0; 44 159 რეალური შემთხვევა; 605 მომხმარებელი; 7 როლი; 57 ტესტი.

**❓ გაურკვეველია:** —

**➡️ რა ვკითხოთ IT-ს:** „ჩვენი მოთხოვნები დოკუმენტში გვაქვს (04). რომელი ნაწილის განხილვით დავიწყოთ: სერვერით თუ მონაცემის წვდომით?“

### Q2. 🟢 რატომ არ შეიძლება Google ცხრილების გაგრძელება? ხომ მუშაობს?

**🗣 მოკლე პასუხი:** „მუშაობს, მაგრამ ზღვარზეა. ცხრილი 30 ათას მწკრივს გადასცდა, მისი წაკითხვა სკრიპტით ~85 წამს გრძელდება და ხანდახან ვარდება. ისტორია არ ინახება, რადგან სტატუსი ზედ იწერება. ხილვადობას ცხრილის გაზიარება მართავს და არა როლები. და ბიზნეს-წესებს ადამიანები იცავენ და არა სისტემა.“

**🔧 ტექნიკური ახსნა:**
- Google Sheets ელცხრილია და არა ტრანზაქციული ბაზა: არ აქვს ბლოკირება მწკრივის დონეზე, შეზღუდვები (constraints) და ისტორია ველის დონეზე;
- Apps Script-ს შესრულების ლიმიტი აქვს: 6 წუთი ჩვეულებრივ ანგარიშზე;
- ერთდროული ჩაწერა `LockService`-ით იმართება;
- „სარკისებრი“ ჩანართები ფორმულებით იწყობა.

**💬 მარტივად რომ გავიგოთ:** ცხრილი რვეულია, რომელშიც ბევრი წერს ერთდროულად. წერა შეიძლება, მაგრამ ვერავინ გეტყვის, ვინ წაშალა წინა ჩანაწერი, და რვეული ვერ შეგაჩერებს, თუ არასწორად წერ.

**📌 ჩვენი პროექტიდან:** ✅ `NAPR_Distributor/README.md`-ში აღწერილია Apps Script-ის ჩავარდნები („Service Spreadsheets failed…“), 3-ჯერადი ხელახალი ცდა და ნაწილობრივი ჩაწერის აღდგენა. ✅ ძველი ცხრილიდან გადმოტანისას 379 დუბლიკატი აღმოჩნდა.

**❓ გაურკვეველია:** —

**➡️ რა ვკითხოთ IT-ს:** „Google Workspace სააგენტოს ოფიციალური ინსტრუმენტია, თუ ცხრილები პირად ანგარიშებზეა? ეს Q46-საც ეხება.“

### Q3. 🔴 რატომ ააშენეთ თავად? რატომ არ გამოიყენეთ მზა პროდუქტი ან არსებული სისტემის მოდული?

**🗣 მოკლე პასუხი:** „ჩვენი სამუშაო პროცესი სპეციფიკურია: „არ ვეთანხმები“ მენეჯერის დადასტურებით, QC მენეჯერის სამი გადაწყვეტილება, CC პრინციპი, ბლოკური განაწილება პროცენტებით. ამას მზა ინსტრუმენტი ღრმა მორგების გარეშე ვერ ასრულებს. თუ სააგენტოს სისტემაში ასეთი მოდული არსებობს, სიამოვნებით განვიხილავთ. ჩვენი წესები და მონაცემის მოდელი დოკუმენტირებულია და ნებისმიერ პლატფორმაზე გადაიტანება.“

**🔧 ტექნიკური ახსნა:** ზოგადი workflow ან ticketing სისტემები (Jira და მისთ.) იძლევა მდგომარეობებსა და როლებს, მაგრამ არ იძლევა:
- **(ა)** REGFIELDALL-ზე „პირველი ოქმის“ კანდიდატების გამოთვლას;
- **(ბ)** ბლოკურ, ფენოვან, პროცენტულ შერჩევას;
- **(გ)** ოქმის რამდენიმე ამზომველსა და რამდენიმე მენეჯერზე მიკუთვნებას;
- **(დ)** სტატისტიკას ჩვენი მეტრიკების ლექსიკონით.

**💬 მარტივად რომ გავიგოთ:** მზა „კოსტიუმი“ არსებობს, მაგრამ ჩვენს ზომაზე ბევრი გადაკერება სჭირდება. გადაკერება კი ზოგჯერ ახლის შეკერვაზე ძვირია.

**📌 ჩვენი პროექტიდან:** ✅ წესები შეთანხმებულია 2026-10-19/20-ზე (`docs/OPEN_QUESTIONS.md`, „მიღებული გადაწყვეტილებები“). ✅ ბირთვული ალგორითმები ძველი პროგრამებიდან გადმოვიდა.

**❓ გაურკვეველია:** ❓ აქვს თუ არა სააგენტოს შიდა BPM ან workflow პლატფორმა.

**➡️ რა ვკითხოთ IT-ს:** „გაქვთ შიდა სტანდარტული პლატფორმა ასეთი აპლიკაციებისთვის? თუ კი, რა მოთხოვნები აქვს?“

### Q4. 🔴 ვინ იქნება ადმინისტრატორი და ვინ დაუჭერს მხარს?

**🗣 მოკლე პასუხი:** „ბიზნეს-ადმინისტრირებას — მომხმარებლებს, როლებს, გუნდებს, კოდებს, განაწილებას — ჩვენ ვაკეთებთ, ორი ადმინი: მე და სალომე დავითაშვილი. ინფრასტრუქტურას (სერვერი, ბაზა, ბექაპი, ქსელი) თქვენთან ვთავაზობთ. კოდის განვითარება და შეცდომების გასწორება ჩვენზეა. ეს გაყოფა წერილობით ჩავწეროთ.“

**🔧 ტექნიკური ახსნა:** RACI-ის შეთავაზება:

| სფერო | ვინ |
|---|---|
| OS, პაჩები, ქსელი, firewall, სერტიფიკატი | IT |
| PostgreSQL-ის ექსპლუატაცია, ბექაპი, აღდგენა | IT (DBA) |
| აპლიკაციის განახლება | ერთად, პროცედურით |
| აპლიკაციის ადმინისტრირება | QC (ლუკა, სალომე) |
| ინციდენტი | პირველ რიგში IT (ინფრასტრუქტურა), მეორეში ჩვენ (აპლიკაცია) |

**💬 მარტივად რომ გავიგოთ:** IT „შენობას“ უვლის: შუქი, წყალი, დაცვა. ჩვენ „მაღაზიას“: თაროები, ფასები, თანამშრომლები.

**📌 ჩვენი პროექტიდან:** ✅ ადმინის როლი მხოლოდ ორ ადამიანს აქვს. ✅ ადმინისტრირება → მომხმარებლები, გუნდები, კოდები, პარამეტრები, მეილები, აუდიტი.

**❓ გაურკვეველია:** ❓ IT-ის ინციდენტების სამსახურის (helpdesk) პროცესი; მორიგეობა არასამუშაო საათებში.

**➡️ რა ვკითხოთ IT-ს:** „ახალი აპლიკაციისთვის რა სტანდარტული ოპერაციული შეთანხმება (SLA / RACI) გაქვთ?“

### Q5. 🟢 IT-სგან რა გჭირდებათ კონკრეტულად?

**🗣 მოკლე პასუხი:** „პილოტისთვის ხუთი რამ: ერთი VM, PostgreSQL, დომენი HTTPS-ით, Google OAuth client და SMTP relay. შემდეგ ეტაპზე წყაროებზე read-only წვდომა: REGFIELDALL, სპორადულის სია, ოქმის დეტალები. სრული სია მიზეზებით და ალტერნატივებით დოკუმენტ 04-შია.“

**🔧 ტექნიკური ახსნა:** იხ. [04 — IT ინფრასტრუქტურის მოთხოვნები](04-IT-ინფრასტრუქტურის-მოთხოვნები.md): R1–R26, პრიორიტეტებითა და ფაზებით.

**💬 მარტივად რომ გავიგოთ:** ჯერ „ოთახი“ (სერვერი), „კარადა“ (ბაზა), „მისამართი“ (დომენი), „შესასვლელი“ (Google) და „ფოსტა“ (SMTP). მერე „გასაღებები“ მონაცემის წყაროებზე.

**📌 ჩვენი პროექტიდან:** ✅ კოდში Google OAuth და SMTP უკვე ჩაშენებულია. ჩასართავად მხოლოდ კონფიგურაცია სჭირდება (`QCP_GOOGLE_*`, `QCP_SMTP_*`).

### Q11. 🟢 რამდენი დისკი დაგჭირდებათ?

**💬 მარტივად რომ გავიგოთ:** პროგრამა ორივე „ენაზე ლაპარაკობს“. Docker კი მზა „ყუთია“, სადაც საიტი ყველა ხელსაწყოსთან ერთად დევს.

**📌 ჩვენი პროექტიდან:** ✅ Python 3.14.5, Windows 11; `.venv` uv-ით.

**❓ გაურკვეველია:** ❓ IT-ის სტანდარტი; აქვთ თუ არა კონტეინერების რეესტრი.

**➡️ რა ვკითხოთ IT-ს:** „Docker image მოგაწოდოთ, თუ სერვერზე გარემოს თქვენ აწყობთ?“

### Q22. 🔴 რატომ PostgreSQL და არა Microsoft SQL Server?

**🗣 მოკლე პასუხი:** „PostgreSQL უფასოა, ჩვენი Pre-QC-ის სერვერული ნაწილი უკვე მასზეა, და გამოცდილებაც გვაქვს. მაგრამ აპლიკაცია ORM-ზეა აგებული, და SQL Server-ზე გადატანა შესაძლებელია. თუ თქვენი სტანდარტი და DBA SQL Server-ისაა, ტესტებს მასზე გავუშვებთ და განსხვავებებს გავასწორებთ.“

**🔧 ტექნიკური ახსნა:**
- SQLAlchemy ორივე დიალექტს უჭერს მხარს (`psycopg` / `pyodbc`);
- SQL Server-ზე შესამოწმებელია:
  - JSON სვეტები (`NVARCHAR(MAX)`);
  - ქართული collation;
  - თარიღის ფუნქციები სტატისტიკაში;
  - ინდექსის სახელების სიგრძე;
- Express ვერსიას ბაზის ზომის ლიმიტი აქვს (10 GB);
- PostgreSQL-ის უპირატესობები: `JSONB`, `ON CONFLICT` upsert, `DISTINCT ON`, Pre-QC hosted-ის მიგრაციები და ტრიგერები.

**💬 მარტივად რომ გავიგოთ:** ორივე კარგი „სეიფია“. ერთი უფასოა და უკვე ვიცნობთ, მეორე შეიძლება თქვენ უკვე გქონდეთ და უვლიდეთ. ორივე გამოდგება.

**📌 ჩვენი პროექტიდან:** ✅ `app/db.py` — SQLite-ის სპეციფიკა მხოლოდ `if _is_sqlite`-შია. ✅ `hosted/README.md` — „SQLite განზრახ დაბლოკილია… სქემა იყენებს JSONB-ს, INET-ს, მასივებსა და ტრიგერებს“.

**❓ გაურკვეველია:** ❓ ⚠️ არცერთ სერვერულ ბაზაზე ტესტი ჯერ არ გაგვიშვია (G1).
