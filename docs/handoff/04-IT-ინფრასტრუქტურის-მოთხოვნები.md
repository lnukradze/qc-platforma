## 0. როგორ არის აწყობილი

თითო მოთხოვნას (R1–R26) აქვს:

1. **რა გვჭირდება** — ტექნიკურად;
2. **რატომ** — ტექნიკური მიზეზი;
3. **რა ფუნქციაა დამოკიდებული**;
4. **სავალდებულოა თუ არჩევითი** და რომელ ფაზაში;
5. **ალტერნატივები**;
6. **რა მოხდება, თუ IT ვერ მოგვცემს**;
7. **🗣 შეხვედრაზე მარტივად** — როგორ ავხსნა ხმამაღლა.

**სავალდებულოობა:**
- **M** — სავალდებულო: ამის გარეშე ფაზა ვერ დაიწყება;
- **S** — სასურველი: ალტერნატივით შეიძლება;
- **O** — არჩევითი.

**ფაზები:**
- **P1** — პილოტი;
- **P2** — წყაროები;
- **P3** — სრული გაშვება;
- **P4** — Pre-QC.

**ზოგადი პრინციპები, რომლებიც ყველა მოთხოვნას ეხება:**
1. **მხოლოდ კითხვა** — სააგენტოს სისტემებში (REGFIELDALL, REDI, SLR) არაფერს ვწერთ.
2. **საკუთარი ასლი** — საჭირო ველების ასლს ვინახავთ და განრიგით ვანახლებთ, ამიტომ წყაროს დატვირთვა მცირეა.
3. **მინიმალური მონაცემი** — მხოლოდ ის ველები, რაც სამუშაოს სჭირდება.
4. **მინიმალური უფლება** — ცალკე სერვისის ანგარიში თითო წყაროზე, მხოლოდ ჩვენი სერვერიდან.
5. **გადატანადობა** — ყველა პარამეტრი კონფიგურაციაშია (`QCP_*` გარემოს ცვლადები), კოდში სერვერი არ წერია.

## 2. თითო მოთხოვნა დეტალურად

### R1. ვირტუალური სერვერი (VM)

1. **რა გვჭირდება:** ერთი VM. 💡 საწყისი შეფასება: **4 vCPU, 8 GB RAM, 100 GB SSD**, PostgreSQL-ის ჩათვლით, თუ ბაზა იმავე VM-ზეა. ბაზის ცალკე სერვერზე განთავსებისას აპლიკაციის VM-ს 2 vCPU და 4 GB RAM ეყოფა (შეფასება).
2. **რატომ:** აპლიკაცია (uvicorn, 2–4 worker), ფონური ამოცანები (ღამის იმპორტი, მეილის რიგი), reverse proxy (თუ VM-ზეა) და PostgreSQL ერთად.
   შეფასების საფუძველი:
   - ≈ 300 მომხმარებელი, ერთდროულად ≈ 40 (`IT_REQUEST.md`-ის შეფასება);
   - ✅ დღევანდელი ბაზა 94 MB-ია, 44 159 შემთხვევაზე;
   - ✅ სტატისტიკა SQLite-ზე 2–3 წმ-ს იღებს;
   - ✅ REGFIELDALL-ის ასლი ≈ 1 GB-ია.
3. **დამოკიდებულია:** ყველაფერი.
4. **M, P1.**
5. **ალტერნატივები:**
   - ადგილი არსებულ აპლიკაციის სერვერზე ან კონტეინერის პლატფორმაზე (Docker host, Kubernetes namespace);
   - მცირე რესურსით დაწყება და გაზრდა გაზომვის შემდეგ.
6. **თუ ვერ მოგვცემს:** პლატფორმა ვერ გაიშვება. დარჩება პროტოტიპი ერთ კომპიუტერზე, რაც საწარმოოსთვის მიუღებელია (სახელმძღვანელო A.2).
7. **🗣 მარტივად:** „ერთი ვირტუალური სერვერი გვჭირდება, საშუალო ოფისის კომპიუტერის სიმძლავრის. ეს შეფასებაა: პილოტზე გავზომავთ და საჭიროებისას შევამცირებთ ან გავზრდით.“

### R2. ოპერაციული სისტემა და runtime

1. **რა გვჭირდება:** Linux (Ubuntu LTS / RHEL-ის ოჯახი) ან Windows Server. Python ≥ 3.12, ვირტუალური გარემოთი; ან Docker Engine, თუ კონტეინერი აირჩევა. სააგენტოს root CA-ს სერტიფიკატი OS-ის საცავში (კორპორატიული TLS-ისთვის). Linux-ზე: systemd სერვისი; Windows-ზე: Windows Service ან კონტეინერი.
2. **რატომ:**
   - ✅ კოდი OS-დამოუკიდებელია (`pathlib`, `QCP_*`);
   - ✅ `truststore` OS-ის სერტიფიკატების საცავს იყენებს, ამიტომ შიდა CA იქ უნდა იყოს. თორემ Google OAuth-ზე და SMTP TLS-ზე კავშირი ჩავარდება;
   - ✅ ტესტირებულია Python 3.14.5-ზე, მოთხოვნა ≥ 3.12.
3. **დამოკიდებულია:** აპლიკაციის გაშვება.
4. **M, P1.**
5. **ალტერნატივები:** ჩვენ ვამზადებთ Docker image-ს, IT კი მხოლოდ კონტეინერის host-ს გვაძლევს. ⚠️ Dockerfile ჯერ არ არსებობს — ეს ჩვენი სამუშაოა.
6. **თუ ვერ მოგვცემს:** —
7. **🗣 მარტივად:** „თქვენი სტანდარტული ოპერაციული სისტემა გამოგვადგება. პროგრამა ორივეზე მუშაობს. Docker-ის „ყუთში“ თუ მოგაწვდით, ინსტალაციაც მარტივი იქნება.“

### R3. PostgreSQL ბაზა

1. **რა გვჭირდება:** PostgreSQL 14+ (💡 სასურველია 16), ცალკე ბაზა (მაგ. `qc`), UTF-8 კოდირებით. ორი მომხმარებელი:
   - `qc_app` — აპლიკაცია: მონაცემის წაკითხვა და ჩაწერა, სქემის შეცვლის გარეშე;
   - `qc_migrator` — სქემის მფლობელი, მიგრაციისთვის.
   superuser არ გვჭირდება. კავშირი მხოლოდ აპლიკაციის სერვერიდან; TLS, თუ ბაზა სხვა VM-ზეა.
2. **რატომ:**
   - ერთდროული ჩაწერა (MVCC);
   - ტრანზაქციები და შეზღუდვები;
   - ბექაპი / PITR;
   - უფლებების მართვა.
   SQLite (✅ პროტოტიპი) ერთ მწერალს უშვებს და ქსელურ წვდომას არ იძლევა (სახელმძღვანელო B.11).
3. **დამოკიდებულია:** ყველა მონაცემი — ოქმები, ისტორია, მომხმარებლები, სესიები.
4. **M, P1.**
5. **ალტერნატივები:** Microsoft SQL Server, თუ ეს სააგენტოს სავალდებულო სტანდარტია. ⚠️ ამ შემთხვევაში ჩვენ ტესტირება და დიალექტის განსხვავებების გასწორება გვიწევს (JSON სვეტები, collation, თარიღები).
6. **თუ ვერ მოგვცემს:** სერვერული ბაზის გარეშე საწარმოო გაშვება შეუძლებელია.
7. **🗣 მარტივად:** „ბაზა ცენტრალური, დაცული „კარადაა“, სადაც საიტი ყველა ჩანაწერს ინახავს. თქვენს არსებულ DB სერვერზე ცალკე ბაზაც საკმარისია. ახალი სერვერი სავალდებულო არ არის.“

⚠️ **ჩვენი მხრიდან (G1, G2):** PostgreSQL-ის დრაივერი ჯერ არ არის დაყენებული და ტესტი არ ჩატარებულა; მიგრაციის ინსტრუმენტი (Alembic) დასამატებელია. 💡 სატესტო PostgreSQL ადრე რომ მივიღოთ, ამ სამუშაოს პარალელურად გავაკეთებთ.

### R4. ბაზის ბექაპი და აღდგენა

1. **რა გვჭირდება:**
   - **P1:** ღამის სრული ბექაპი (`pg_dump -Fc` ან თქვენი ინსტრუმენტი), მინიმუმ 14 დღის შენახვით;
   - **P3:** PITR — base backup + WAL-ის არქივი (pgBackRest / Barman / თქვენი ინსტრუმენტი);
   - ბექაპი **სხვა მედიაზე ან ლოკაციაზე** უნდა იყოს და დაშიფრული;
   - აღდგენის ტესტი კვარტალში ერთხელ.
2. **რატომ:** QC-ის ისტორია და გადაწყვეტილებები ორგანიზაციის ჩანაწერებია. 💡 შეთავაზება: RPO ≤ 15 წთ, RTO ≤ 4 სთ (❓ ხელმძღვანელობისა და IT-ის დასამტკიცებელი).
3. **დამოკიდებულია:** მონაცემის დაკარგვისგან დაცვა.
4. **M:** P1 — ღამის; P3 — PITR.
5. **ალტერნატივები:**

### R8. Reverse proxy / load balancer

1. **რა გვჭირდება:**
   - HTTPS-ის მიღება (TLS termination) და გადაცემა აპლიკაციაზე (`http://127.0.0.1:8200` ან შიდა IP);
   - მოთხოვნის ზომა ≥ 12 MB (ფოტო ≤ 10 MB + ფორმა);
   - timeout ≥ 120 წმ (განაწილების გადახედვა ათასობით ჩანაწერზე. ❓ PostgreSQL-ზე გასაზომია);
   - `X-Forwarded-For` და `X-Forwarded-Proto` თავსართები;
   - HTTP → HTTPS გადამისამართება; HSTS;
   - წვდომის ლოგი **query string-ის გარეშე**, ან მისი ნიღბვით, რომ OAuth-ის `code` ლოგში არ ჩაიწეროს.
2. **რატომ:**
   - Python-ის აპლიკაციის სერვერი ინტერნეტზე პირდაპირ არ უნდა ჩანდეს;
   - ⚠️ G4: აპლიკაციას proxy-ს IP-ისა და თავსართების ცოდნა სჭირდება, `--proxy-headers --forwarded-allow-ips`-ისთვის. თორემ cookie `Secure`-ის გარეშე დარჩება, და აუდიტში არასწორი IP ჩაიწერება.
3. **დამოკიდებულია:** HTTPS, ატვირთვა, ლოგები.
4. **M, P1.**
5. **ალტერნატივები:**
   - nginx, ან IIS + ARR, ჩვენს VM-ზე;
   - სააგენტოს ცენტრალური load balancer / WAF.
6. **თუ ვერ მოგვცემს:** proxy ჩვენს VM-ზე დავაყენებთ (nginx), ოღონდ სერტიფიკატი თქვენგან გვჭირდება.
7. **🗣 მარტივად:** „proxy შენობის „მიმღებია“: დაცული შესასვლელი, რომელიც სტუმარს სწორ ოთახში ატარებს. თქვენი სტანდარტული მიმღები გვირჩევნია.“
