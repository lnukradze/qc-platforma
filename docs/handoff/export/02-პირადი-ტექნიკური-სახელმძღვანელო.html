A. სერვერები და ჰოსტინგი

A.1 რა არის სერვერი

1. ტექნიკური განმარტება. სერვერი არის კომპიუტერი (ფიზიკური ან ვირტუალური), რომელზეც მუდმივად გაშვებული პროგრამები ქსელში შემოსულ მოთხოვნებს ემსახურება. „სერვერი“ ორ რამეს ნიშნავს: მანქანას (host, VM) და პროგრამას (სერვისს), რომელიც ამ მანქანაზე კონკრეტულ პორტზე „უსმენს“, მაგალითად ვებ-სერვერი 443-ზე ან PostgreSQL 5432-ზე. დღეს სერვერების უმეტესობა ვირტუალური მანქანაა (VM): ერთ ფიზიკურ მანქანაზე ჰიპერვიზორი (VMware, Hyper-V, KVM) რამდენიმე იზოლირებულ „კომპიუტერს“ უშვებს, საკუთარი CPU-ს, RAM-ის, დისკისა და IP-ის წილით.

2. მარტივად რომ ავხსნათ. სერვერი არის კომპიუტერი, რომელიც არასოდეს ითიშება და სხვებს ემსახურება. მე ჩემს კომპიუტერთან ვზივარ; სერვერთან არავინ ზის. ის სადღაც სერვერების ოთახშია და დღე-ღამე ელოდება, როდის ვინმე „დააკაკუნებს“ (გახსნის საიტს).

3. ჩვენს პროექტში. ✅ დღეს „სერვერი“ ჩემი კომპიუტერია: run.bat უშვებს პროგრამას uvicorn, რომელიც პორტ 8200-ზე უსმენს (scripts/run_local.py). 💡 საწარმოოში ეს იგივე პროგრამა სააგენტოს VM-ზე იმუშავებს.

4. რატომ გვჭირდება. ≈ 300 თანამშრომელმა სხვადასხვა ადგილიდან (ოფისი, ველი, ტელეფონი) ერთსა და იმავე მონაცემთან უნდა იმუშაოს, ნებისმიერ დროს. ამისთვის საჭიროა ერთი ადგილი, რომელიც ყოველთვის ჩართულია და ყველასთვის ხელმისაწვდომია.

5. როგორ მუშაობს კულისებში. ბრაუზერი DNS-ით ადგენს სერვერის IP-ს (მაგ. qc.<დომენი> → 10.x.x.x), შემდეგ ამ IP-ის კონკრეტულ პორტთან TCP კავშირს ხსნის. სერვერის ოპერაციული სისტემა კავშირს იმ პროგრამას გადასცემს, რომელიც ამ პორტზე უსმენს. პროგრამა მოთხოვნას ამუშავებს და პასუხს აბრუნებს.

6. რა შეიძლება აირიოს.

  • სერვერი გადაიტვირთა და პროგრამა თავისით არ ჩაირთო (სერვისად არ არის დაყენებული);
  • დისკი გაივსო;
  • Firewall-ი პორტს ბლოკავს;
  • VM-ს რესურსი არ ჰყოფნის.

7. რას იკითხავს IT. „ფიზიკური სერვერი გჭირდებათ თუ VM? რა OS? რამდენი რესურსი?“

8. როგორ ვუპასუხო. „ფიზიკური არ გვჭირდება. ერთი VM საკმარისია, Linux ან Windows Server — თქვენი სტანდარტით. რესურსის შეფასება მოგვაქვს (დოკუმენტი 04, R1), მაგრამ ის შეფასებაა და პილოტზე გავზომავთ.“

A.2 რატომ არ შეიძლება ყველაფერი VS Code-იდან ან ერთი თანამშრომლის კომპიუტერიდან

1. ტექნიკური განმარტება. VS Code კოდის რედაქტორია (IDE) და არა გაშვების გარემო (runtime). ის კოდს წერს და შეუძლია მისი დროებით გაშვება დეველოპმენტისთვის. სამუშაო კომპიუტერი კი საწარმოო ჰოსტინგისთვის არ გამოდგება:

  • არ აქვს მაღალი ხელმისაწვდომობა (ითიშება, იძინებს, ახლდება);
  • მისი IP დინამიკურია;
  • firewall და ანტივირუსი მის „სერვერობას“ ზღუდავს;
  • არ აქვს ბექაპი, მონიტორინგი და ფიზიკური დაცვა;
  • მომხმარებლის სესიაზეა დამოკიდებული (ვინც გამოვა სისტემიდან, პროგრამაც ჩერდება);
  • უსაფრთხოების პოლიტიკით სამუშაო სადგური ქსელში სერვისს არ უნდა აწვდიდეს.

2. მარტივად რომ ავხსნათ. VS Code ჩემი „სახელოსნოა“, სადაც საიტს ვაწყობ. ჩემი კომპიუტერი კი „საცხოვრებელი სახლია“ და არა „მაღაზია“. როცა სახლში არ ვარ ან შუქი ქრება, მაღაზია იკეტება. ამიტომ საიტი ისეთ ადგილას უნდა იდგეს, რომელიც ყოველთვის ღიაა და დაცული.

3. ჩვენს პროექტში.

  • ✅ run_lan.bat ტელეფონზე ჩვენებისთვის ჩემს კომპიუტერს ქსელში ხსნის, ოღონდ PIN-ით და დროებით. ფანჯარაში თავად წერია: „მხოლოდ მოკლე ჩვენებისთვის“ (scripts/serve_lan.py).
  • ✅ ძველი განაწილების პროგრამა სწორედ ამ პრობლემის მაგალითია: ის ერთ კომპიუტერზეა და იმ კომპიუტერის გარეშე განაწილება ვერ ხდება.

4. რატომ გვჭირდება ეს გაგება. IT-მ შეიძლება იკითხოს: „დღეს ხომ მუშაობს, რატომ გჭირდებათ სერვერი?“ პასუხი: დღეს მუშაობს ერთი ადამიანისთვის, დემოსთვის, და არა 300 ადამიანისთვის, ყოველდღიურად.

5. კულისებში. კომპიუტერის ჩაძინება ან გადატვირთვა პროცესს კლავს. VPN-ის გათიშვა ქსელურ დისკს (Z:) აქრობს. Windows-ის განახლება ღამით გადატვირთავს. ჩემი პაროლის შეცვლა კი გაშვებულ სკრიპტებს წვდომას დაუკარგავს.

6. რა შეიძლება აირიოს. თუ ვინმე „დროებით“ ჩემი კომპიუტერიდან დაიწყებს მუშაობას:

  • მონაცემი ერთ დისკზე იქნება, ბექაპის გარეშე;
  • ჩემი შვებულება სისტემის შვებულება გახდება.

7. IT იკითხავს. „რატომ არ შეიძლება, უბრალოდ თქვენს კომპიუტერზე ეშვებოდეს და ქსელში გავხსნათ?“

8. პასუხი. „სამუშაო სადგური ხელმისაწვდომობას, ბექაპსა და უსაფრთხოებას ვერ უზრუნველყოფს. მასზე ჩვენ სისტემას ვაწყობთ და ვამოწმებთ; სამუშაო ვერსია თქვენს მართულ სერვერზე უნდა იდგეს.“

A.3 localhost, შიდა სერვერი, ღრუბელი და on-premises — რა განსხვავებაა

1. ტექნიკური განმარტება.

ტერმინი რას ნიშნავს ვინ მიწვდება
localhost (127.0.0.1) „ეს კომპიუტერი“. ამ მისამართზე გაშვებული სერვისი მხოლოდ იმავე მანქანიდან იხსნება მხოლოდ მე
LAN / შიდა მისამართი (10.x, 192.168.x, 0.0.0.0-ზე მოსმენა) სერვისი ლოკალური ქსელის ინტერფეისზე უსმენს იმავე შიდა ქსელში მყოფი ყველა
შიდა (on-premises) სერვერი ორგანიზაციის საკუთარ მონაცემთა ცენტრში მდგარი, მისი IT-ის მიერ მართული მანქანა შიდა ქსელი; გარედან — VPN-ით ან გამოქვეყნებით (reverse proxy / DMZ)
ღრუბელი (Render, AWS, Azure…) სხვა კომპანიის მონაცემთა ცენტრში ქირით აღებული რესურსი ინტერნეტიდან, თუ ასეა კონფიგურირებული
ჰიბრიდი ნაწილი შიდაა, ნაწილი ღრუბელში —

2. მარტივად რომ ავხსნათ.

  • localhost ჩემი ოთახია: მხოლოდ მე ვარ შიგნით.
  • LAN სართულია: ვინც ამ სართულზეა, შემოვა.
  • on-premises სააგენტოს საკუთარი შენობაა, საკუთარი დაცვით.
  • ღრუბელი ნაქირავები ოფისია სხვის შენობაში: მოსახერხებელია, მაგრამ გასაღები სხვასაც აქვს და შენობა სხვა ქვეყანაში შეიძლება იყოს.

3. ჩვენს პროექტში.

  • ✅ run.bat → 127.0.0.1:8200 (localhost);
  • ✅ run_lan.bat → 0.0.0.0:8200 (LAN, PIN-ით);
  • ✅ ძველი სტატისტიკის პანელის DEPLOY.md აღწერს Render-სა და Neon-ს — ეს ღრუბელია, Frankfurt-ში;
  • 💡 ახალი პლატფორმისთვის მიზანია on-premises, სააგენტოს სერვერი (OPEN_QUESTIONS.md #5).

4. რატომ არის მნიშვნელოვანი. QC მონაცემი შეიცავს თანამშრომლების სახელებს, QC კომენტარებს (ზოგჯერ მოქალაქეების სახელებით) და პირად ნომრებს. სახელმწიფო უწყებისთვის მონაცემის ადგილმდებარეობა და კონტროლი პოლიტიკისა და კანონის საკითხია.

5. კულისებში. იმისთვის, რომ ველიდან ტელეფონით შიდა სერვერზე შევიდეთ, ორი გზა არსებობს:

  • (ა) VPN — ტელეფონი შიდა ქსელის ნაწილი ხდება;
  • (ბ) გამოქვეყნება — reverse proxy ან სააგენტოს load balancer საჯარო HTTPS მისამართზე იღებს მოთხოვნას და შიდა სერვერს გადასცემს. ჩვეულებრივ, ეს DMZ-ში ხდება — ქსელის ნაწილში, რომელიც გარედანაც ჩანს და შიდა ქსელისგან გამოყოფილია.

6. რა შეიძლება აირიოს.

  • მხოლოდ შიდა წვდომა → ველი ტელეფონიდან ვერ შედის;
  • საჯარო წვდომა ზედმეტი დაცვის გარეშე → თავდასხმის ზედაპირი იზრდება.

7. IT იკითხავს. „საიტი გარედან უნდა იხსნებოდეს?“

8. პასუხი. „ველი ტელეფონით და პლანშეტით მუშაობს, ამიტომ გარედან წვდომა გვჭირდება: ან საჯარო HTTPS, ან VPN. რომელი, თქვენი პოლიტიკით გადაწყვიტეთ. აპლიკაცია ორივეზე მუშაობს (❓ IT-ის გადასაწყვეტია).“

A.4 IP, პორტი, პროცესი — როგორ „ესმის“ პროგრამას

1. ტექნიკური განმარტება.

  • IP მისამართი მანქანის ქსელური მისამართია.
  • პორტი (0–65535) კონკრეტული სერვისის „კარია“ ამ მანქანაზე. სტანდარტული პორტები: HTTP 80, HTTPS 443, PostgreSQL 5432, SQL Server 1433, SMTP 25/587, SSH 22, RDP 3389.
  • პროცესი გაშვებული პროგრამაა. ის OS-ს სთხოვს, რომ კონკრეტულ IP:პორტზე „მოუსმინოს“ (bind/listen).
  • 127.0.0.1-ზე მოსმენა მხოლოდ ლოკალურ კავშირს იღებს, 0.0.0.0-ზე მოსმენა კი ყველა ინტერფეისიდან.

2. მარტივად რომ ავხსნათ. IP შენობის მისამართია, პორტი ბინის ნომერი. ვებ-საიტი 443-ე ბინაშია, ბაზა 5432-ეში. თუ კარი (firewall) დაკეტილია, მისამართის ცოდნა არ გიშველის.

3. ჩვენს პროექტში.

  • ✅ აპლიკაცია პორტ 8200-ზე უსმენს (QCP_PORT);
  • 💡 საწარმოოში მომხმარებელი 443-ზე შევა (proxy), proxy კი 8200-ს მიმართავს შიგნით;
  • 💡 PostgreSQL 5432-ზე იქნება და მას მხოლოდ აპლიკაციის სერვერი უნდა მიწვდეს.

4. რატომ. IT-ის firewall-ის წესები სწორედ „ვის → რომელ IP:პორტზე“ ფორმატით იწერება. ეს უნდა ვიცოდეთ, რომ მოთხოვნა სწორად ჩამოვაყალიბოთ.

5. კულისებში. Firewall პაკეტს წესების მიხედვით ატარებს ან აჩერებს. ეს წესები შეიძლება იყოს VM-ზე (Windows Firewall, iptables/nftables) და ქსელურ მოწყობილობაზეც.

6. რა შეიძლება აირიოს.

  • „კავშირი ვერ დამყარდა“ (connection refused) — სერვისი არ უსმენს ან პორტი არასწორია;
  • „timeout“ — firewall ჩუმად აგდებს პაკეტს.

7. IT იკითხავს. „რომელი პორტები უნდა გავხსნათ?“

8. პასუხი.

  • „შემომავალი: მხოლოდ 443 proxy-ზე (და 80, HTTPS-ზე გადამისამართებისთვის).
  • შიგნით: proxy → აპლიკაცია 8200, აპლიკაცია → PostgreSQL 5432.
  • გამავალი: Google-ის OAuth-ი 443-ზე და SMTP relay (587 ან თქვენი პორტი).
  • წყაროები: იმის მიხედვით, რა გზას აირჩევთ (view → 5432 ან 1433; ფაილი → SMB 445 ან SFTP 22).“

A.5 აპლიკაციის სერვერი (uvicorn) და worker-ები

1. ტექნიკური განმარტება. აპლიკაციის სერვერი არის პროცესი, რომელიც HTTP-ს იღებს და აპლიკაციის კოდს იძახებს. Python-ში ვებ-აპლიკაციები სტანდარტული ინტერფეისით ერთვება: WSGI (სინქრონული — Flask) ან ASGI (ასინქრონული — FastAPI). uvicorn ASGI სერვერია. worker აპლიკაციის ერთი ასლი-პროცესია. რამდენიმე worker პარალელურად ემსახურება მოთხოვნებს და რამდენიმე CPU ბირთვს იყენებს. ამის საშუალებას იძლევა uvicorn --workers N ან gunicorn + uvicorn.workers.UvicornWorker (gunicorn მხოლოდ Linux-ზე მუშაობს).

2. მარტივად რომ ავხსნათ. uvicorn რესტორნის „მიმტანია“: შეკვეთას იღებს, სამზარეულოს (ჩვენს კოდს) გადასცემს და კერძს მოაქვს. worker-ები მიმტანების რაოდენობაა. ერთი მიმტანი ბევრ მაგიდას ემსახურება, ოთხი კი პიკის საათზე უკეთ გაართმევს თავს.

3. ჩვენს პროექტში.

  • ✅ დღეს ერთი uvicorn პროცესი ეშვება, --reload-ის გარეშე (scripts/run_local.py);
  • ⚠️ დღეს რამდენიმე worker ვერ ჩაირთვება: განაწილების გადახედვა ერთი პროცესის მეხსიერებაში ინახება (Handoff G6). ჯერ ეს უნდა გასწორდეს.

4. რატომ. worker-ების რაოდენობა ნაწილობრივ განსაზღვრავს, რამდენ ერთდროულ მოთხოვნას გაუძლებს სისტემა.

5. კულისებში.

  • ჩვენი მარშრუტების უმეტესობა სინქრონული ფუნქციაა (def). FastAPI ასეთ ფუნქციებს thread pool-ში უშვებს, ამიტომ ერთი worker-იც რამდენიმე მოთხოვნას ერთდროულად ამუშავებს;
  • Python-ის GIL ერთ პროცესში CPU-ს ინტენსიურ სამუშაოს ზღუდავს. ბაზის მოლოდინი კი GIL-ს ათავისუფლებს;
  • თითო worker ცალკე იტვირთება მეხსიერებაში. რამდენი MB სჭირდება თითოს, პილოტზე უნდა გავზომოთ.

6. რა შეიძლება აირიოს.

  • ზედმეტად ბევრი worker → ბაზის კავშირები ამოიწურება;
  • ზედმეტად ცოტა → რიგი იქმნება;
  • მდგომარეობის მეხსიერებაში შენახვა (G6) → worker-ებს შორის აირევა.

7. IT იკითხავს. „რამდენ პროცესს გაუშვებთ? როგორ ირთვება გადატვირთვის შემდეგ?“

8. პასუხი. „საწყისად 2–4 worker-ს ვგეგმავთ, რაც პილოტზე დაზუსტდება. პროცესი სისტემურ სერვისად იქნება დაყენებული (Linux-ზე systemd, Windows-ზე სერვისი ან კონტეინერი), ავტომატური რესტარტით. რამდენიმე worker-ისთვის ერთ კომპონენტს ვასწორებთ, ესაა ჩვენი სამუშაო პილოტამდე.“

A.6 Reverse proxy

1. ტექნიკური განმარტება. Reverse proxy (nginx, Apache, IIS + ARR, HAProxy, ან სააგენტოს load balancer) არის სერვერი, რომელიც კლიენტის მოთხოვნას იღებს და შიდა აპლიკაციის სერვერს გადასცემს. მისი ფუნქციები:

  • TLS termination — HTTPS-ის დაშიფვრა და გაშიფვრა;
  • სტატიკური ფაილების გაცემა;
  • მოთხოვნის ზომის და დროის ლიმიტები;
  • წვდომის ჟურნალი;
  • ბალანსირება რამდენიმე ასლს შორის;
  • IP-ის შეზღუდვა;
  • X-Forwarded-For / X-Forwarded-Proto თავსართების დამატება, რომ აპლიკაციამ იცოდეს კლიენტის ნამდვილი IP და პროტოკოლი.

2. მარტივად რომ ავხსნათ. reverse proxy შენობის მიმღებია. სტუმარი მას ხვდება; მიმღები ამოწმებს და სწორ კაბინეტში უშვებს. თავად კაბინეტი (ჩვენი აპლიკაცია) ქუჩიდან არ ჩანს.

3. ჩვენს პროექტში.

  • ✅ დღეს proxy არ არის;
  • 💡 საწარმოოში საჭიროა: HTTPS-ისთვის, ფოტოს ატვირთვის ზომის ლიმიტისთვის (აპლიკაცია ≤ 10 MB-ს ამოწმებს, proxy-ზეც ეს ზღვარი უნდა იყოს) და ლოგებისთვის;
  • ⚠️ აპლიკაციამ proxy-ს თავსართები უნდა მიიღოს, თორემ cookie-ს Secure ნიშანი და აუდიტის IP არასწორი იქნება (Handoff G4).

4. რატომ. Python-ის აპლიკაციის სერვერს პირდაპირ ინტერნეტზე არ გამოაჩენენ: TLS-ის მართვა, ნელი კლიენტებისგან დაცვა და ლოგები proxy-ს საქმეა. IT-ს ხშირად ერთი სტანდარტული proxy აქვს ყველა საიტისთვის.

5. კულისებში.

  • კლიენტი → https://qc.<დომენი>:443 → proxy შიფრს ხსნის → http://127.0.0.1:8200 → აპლიკაცია;
  • proxy ამატებს X-Forwarded-Proto: https-ს და X-Forwarded-For: <კლიენტის IP>-ს;
  • uvicorn ამ თავსართებს ენდობა მხოლოდ მაშინ, თუ გაშვებულია --proxy-headers --forwarded-allow-ips=<proxy-ს IP>-ით.

6. რა შეიძლება აირიოს.

  • Google redirect URI-ში http აღმოჩნდება https-ის ნაცვლად → Google შესვლას უარყოფს (redirect_uri_mismatch). ამიტომ QCP_BASE_URL ცხადად უნდა მიეთითოს;
  • ატვირთვა ჩავარდება 413-ით (proxy-ს ლიმიტი ნაკლებია 10 MB-ზე).

7. IT იკითხავს. „თქვენ დააყენებთ nginx-ს, თუ ჩვენს load balancer-ს გამოიყენებთ?“

8. პასუხი. „თქვენი სტანდარტი გვირჩევნია. ჩვენ გვჭირდება: HTTPS, მოთხოვნის ზომა ≥ 10 MB, X-Forwarded-* თავსართები და მათი IP, რომ აპლიკაციაში ნდობის სიაში ჩავწეროთ.“

A.7 ბაზის სერვერი

1. ტექნიკური განმარტება. მონაცემთა ბაზის მართვის სისტემა (DBMS, მაგ. PostgreSQL) ცალკე სერვერული პროცესია. ის მონაცემს დისკზე ინახავს და კლიენტებს ქსელით (TCP 5432) ემსახურება. მისი ფუნქციებია ტრანზაქციები, ერთდროული წვდომა, უფლებები და ბექაპი. SQLite ამის საპირისპიროდ ჩაშენებული ბიბლიოთეკაა: ბაზა ერთი ფაილია, რომელსაც აპლიკაციის პროცესი პირდაპირ კითხულობს. ცალკე სერვერი იქ არ არსებობს.

2. მარტივად რომ ავხსნათ.

  • SQLite რვეულია, რომელიც ჩემს მაგიდაზე დევს: სწრაფია და მარტივი, მაგრამ ერთდროულად ერთი წერს.
  • PostgreSQL არქივია, თავისი არქივარიუსით: ბევრი ადამიანი ერთდროულად ითხოვს და აბრუნებს საქაღალდეებს, არქივარიუსი კი წესრიგს იცავს.

3. ჩვენს პროექტში.

  • ✅ დღეს SQLite: data/platform.db, WAL რეჟიმი, foreign_keys=ON (app/db.py);
  • 💡 საწარმოოში PostgreSQL 16: ან იმავე VM-ზე, ან სააგენტოს DB სერვერზე.

4. რატომ. ერთდროული ჩაწერა, ბექაპის ინსტრუმენტები, უფლებების მართვა და მონიტორინგი სერვერულ DBMS-ს აქვს. დაწვრილებით: B.11.

5. კულისებში. აპლიკაცია PostgreSQL-ს connection string-ით უკავშირდება:

postgresql+psycopg://qc_app:<პაროლი>@db-host:5432/qc

SQLAlchemy კავშირების „აუზს“ (pool) ინახავს, რომ ყოველ მოთხოვნაზე ახალი კავშირი არ გაიხსნას.

6. რა შეიძლება აირიოს.

  • კავშირების ლიმიტი (max_connections, ნაგულისხმევად 100) ამოიწურება, თუ worker-ები × pool ზედმეტია;
  • ქსელის შეფერხება აპლიკაციასა და ბაზას შორის ყველა გვერდს ანელებს.

7. IT იკითხავს. „ბაზა ჩვენს არსებულ კლასტერზე იქნება, თუ ცალკე?“

A.13 ჩავარდნა, კავშირის დაკარგვა, გადატვირთვა

1. ტექნიკური განმარტება.

სცენარი ქცევა
პროცესის ჩავარდნა სერვისის მენეჯერი (systemd / Docker) ხელახლა უშვებს. მიმდინარე მოთხოვნები იკარგება; დაუსრულებელი ტრანზაქციები ბაზა თავად აბრუნებს (rollback)
VM-ის გადატვირთვა სერვისები ჩატვირთვისას ირთვება. PostgreSQL ჩამოწერილ WAL-ს „თავიდან ატარებს“ (crash recovery), ამიტომ დადასტურებული (commit) მონაცემი არ იკარგება
ქსელის დაკარგვა წყაროსთან იმპორტი ჩავარდება და ჟურნალში ჩაიწერება; საიტი ბოლო ჩატვირთულ მონაცემზე მუშაობს
ქსელის დაკარგვა მომხმარებელთან გვერდი ვერ იხსნება; გაუგზავნელი ფორმა იკარგება (ბრაუზერის მხარეს)

2. მარტივად რომ ავხსნათ. თუ სერვერი ჩაქრა და ისევ ჩაირთო, ყველაფერი, რაც „შენახვა“ ღილაკით უკვე შეინახა, ადგილზე დახვდება. იკარგება მხოლოდ ის, რაც ზუსტად იმ წამს იგზავნებოდა. მომხმარებელს ხელახლა მოუწევს ღილაკზე დაჭერა.

  • ✅ ყოველი მოქმედება ერთ ტრანზაქციაშია (db.commit(), შეცდომისას rollback) — routes/items.action;
  • ✅ სესიები ბაზაში ინახება, ამიტომ სერვერის გადატვირთვის შემდეგ მომხმარებელი შესული რჩება (12 სთ-მდე);

  • ✅ ძველი Distributor-იც ქსელის მიუწვდომლობისას ბოლო ჩატვირთულ მონაცემს იყენებს — იგივე პრინციპი.

4. რატომ. IT-ს აინტერესებს, რა დაიკარგება ინციდენტის დროს (RPO) და რამდენ ხანში აღდგება (RTO). იხ. A.16.

5. კულისებში. PostgreSQL ჯერ WAL-ში (write-ahead log) წერს და მერე მონაცემის ფაილებში. commit დაბრუნდება მხოლოდ მაშინ, როცა WAL დისკზე ჩაიწერა (fsync). ამიტომ commit-ის შემდეგ ჩავარდნაც კი მონაცემს არ კარგავს.

  • დისკის ფიზიკური დაზიანება — სწორედ ამისთვის არის ბექაპი;
  • მეილი, რომელიც „იგზავნებოდა“, როცა პროცესი ჩავარდა (G7) — outbox-ით გამოსწორდება.

A.14 განთავსება და განახლება (deployment)

1. ტექნიკური განმარტება. Deployment არის კოდის ახალი ვერსიის სერვერზე გადატანა და გაშვება. ტიპური ნაბიჯებია:

  1. ვერსიის მომზადება (git tag ან image);
  2. ტესტები;
  3. ბაზის ბექაპი;
  4. მიგრაციის გაშვება (Alembic);
  5. ახალი კოდის გაშვება;
  6. შემოწმება (health check, smoke test);
  7. საჭიროებისას დაბრუნება (rollback).

გარემოები: dev (ჩემი კომპიუტერი) → test/staging (სატესტო სერვერი, ასლი ან ანონიმიზებული მონაცემი) → production.

შეფერხების გარეშე განახლების ხერხები:

  • rolling restart — worker-ების მორიგეობით გადატვირთვა;
  • blue/green — ორი ასლი, proxy გადართვა;
  • მიგრაციები, რომლებიც ძველსა და ახალ კოდთან ერთდროულად თავსებადია (expand → migrate → contract).

2. მარტივად რომ ავხსნათ. ახალი ვერსია ჯერ „სარეპეტიციო დარბაზში“ მოწმდება. მერე, ღამით ან შესვენებისას, სამუშაო სერვერზე იცვლება. ძველი ვერსია მზად გვაქვს, რომ რამე თუ არ გამოვა, უკან დავაბრუნოთ. პატარა განახლებას მომხმარებელი ვერც შეამჩნევს.

3. ჩვენს პროექტში.

  • ✅ დღეს deployment არ არსებობს: კოდი ჩემს კომპიუტერზეა;
  • ⚠️ პროექტის საქაღალდე ჯერ git-ის რეპოზიტორია არ არის (აუდიტისას: not a git repository). .gitignore მზადაა და data/-ს გამორიცხავს;
  • 💡 საჭიროა:
    • (ა) ვერსიის კონტროლი (სააგენტოს GitLab/GitHub/Azure DevOps ან სხვა);
    • (ბ) Alembic (G2);
    • (გ) სატესტო გარემო;
    • (დ) განახლების წერილობითი პროცედურა.

4. რატომ. IT ცვლილებების მართვის (change management) წესს ითხოვს: ვინ, როდის, რას აყენებს და როგორ ბრუნდება უკან.

5. კულისებში. ჩვენი სისტემა მცირე შეფერხებას იტანს: სესია ბაზაშია, ამიტომ რესტარტი მომხმარებელს არ „აგდებს“. რამდენიმე worker-ით rolling restart უკვე შეუმჩნეველი იქნება.

6. რა შეიძლება აირიოს.

  • მიგრაცია წარუმატებელია → საჭიროა ბექაპი და დაბრუნების გეგმა;
  • ახალი კოდი ძველ სქემას ელოდება;
  • „სერვერზე ხელით შეცვლილი ფაილი“ — ასეთი ცვლილება არასოდეს უნდა ხდებოდეს.

7. IT იკითხავს. „განახლებას ვინ აყენებს — თქვენ თუ ჩვენ? შეფერხება იქნება?“

8. პასუხი. „გვინდა წერილობითი პროცედურა, რომელიც ორივე მხარეს შეეძლება. ჩვენ ვამზადებთ ვერსიას და მიგრაციას, თქვენი წესით ვაყენებთ, ჯერ სატესტო გარემოზე. ჩვეულებრივი განახლება წამებს გრძელდება და სესიები არ იკარგება. დიდი ცვლილება შეთანხმებულ ფანჯარაში ჩატარდება.“

A.16 აღდგენა (recovery): RPO და RTO

1. ტექნიკური განმარტება.

  • RPO (Recovery Point Objective) — რა მაქსიმალური პერიოდის მონაცემის დაკარგვაა დასაშვები.
  • RTO (Recovery Time Objective) — რამდენ ხანში უნდა აღდგეს სისტემა.

ღამის pg_dump RPO-ს ≤ 24 საათამდე ამცირებს. PITR (base backup + WAL არქივი) RPO-ს წუთებამდე ამცირებს. აღდგენის გეგმა უნდა იყოს დოკუმენტირებული და პერიოდულად გამოცდილი (restore test).

2. მარტივად რომ ავხსნათ.

  • RPO ნიშნავს: „რამდენი სამუშაოს დაკარგვას ვიტანთ?“ — ერთი დღის? ერთი საათის?
  • RTO ნიშნავს: „რამდენ ხანს შეგვიძლია უსისტემოდ ვიყოთ?“ — ერთი საათი? ერთი დღე?

რაც უფრო მცირეა ეს ციფრები, მით მეტი ღირს. ამიტომ ციფრები ხელმძღვანელობამ და IT-მ ერთად უნდა გადაწყვიტონ.

3. ჩვენს პროექტში.

  • ✅ დღეს ბექაპი არ კეთდება;
  • ✅ ერთადერთი „აღდგენა“ build_db.py-ია, რომელიც ძველი ცხრილიდან ხელახლა აწყობს ბაზას. საწარმოოში ეს აღდგენა არ არის, რადგან ახალ სისტემაში შექმნილ სამუშაოს ძველი ცხრილი აღარ შეიცავს;
  • 💡 შეთავაზება: RPO ≤ 15 წთ (PITR), RTO ≤ 4 სთ სამუშაო დღეს. ❓ დასამტკიცებელია.

4. რატომ. QC-ის ისტორია სამუშაოს მტკიცებულებაა: ვინ რა გადაწყვიტა. მისი დაკარგვა დღევანდელი ცხრილის დაკარგვაზე უარესია.

5. კულისებში. აღდგენისას:

  1. base backup აღდგება;
  2. WAL „ითამაშება“ საჭირო წუთამდე;
  3. აპლიკაცია ახალ ბაზას უკავშირდება;
  4. ფოტოები ცალკე, ფაილების ბექაპიდან აღდგება.

6. რა შეიძლება აირიოს.

  • ბექაპი კეთდებოდა, მაგრამ არასოდეს შემოწმებულა და აღდგენისას აღმოჩნდა დაზიანებული;
  • ბაზა აღდგა, ფოტოები კი არა.

7. IT იკითხავს. „რა RPO/RTO გჭირდებათ?“

8. პასუხი. „ვთავაზობთ RPO 15 წუთს და RTO 4 საათს. თუ თქვენი სტანდარტული ვარიანტი ღამის ბექაპია (RPO 24 სთ), პილოტისთვის მისაღებია, მაგრამ სრული გაშვებისთვის PITR გვინდა. აღდგენის ტესტი წელიწადში ერთხელ მაინც უნდა ჩატარდეს.“

B. SQL და მონაცემთა ბაზები

B.1 რატომ სჭირდება პლატფორმას ბაზა

1. ტექნიკური განმარტება. მონაცემთა ბაზა (DBMS) მონაცემის მუდმივ (persistent) შენახვას, ერთდროულ უსაფრთხო წვდომას, მთლიანობის წესებს (constraints), ტრანზაქციებს, სწრაფ ძებნას (ინდექსები), უფლებებს და აღდგენას უზრუნველყოფს. ვებ-აპლიკაცია თავად „უმეხსიერო“ (stateless) უნდა იყოს: მისი პროცესი ნებისმიერ დროს შეიძლება გადაიტვირთოს, მდგომარეობა კი ბაზაში ცხოვრობს.

2. მარტივად რომ ავხსნათ. PostgreSQL არის ცენტრალური, დაცული ადგილი, სადაც საიტი ყველა ინფორმაციას ინახავს და ალაგებს. საიტი თავად მხოლოდ „ფანჯარაა“; ყველაფერი, რაც უნდა დარჩეს, ბაზაში იწერება. საიტი რომ გადაიტვირთოს, ინფორმაცია ადგილზე რჩება.

  • სტატუსის მოთხოვნები (verdict_requests);

B.2 ცხრილი, მწკრივი, სვეტი — რელაციური მოდელი

1. ტექნიკური განმარტება. რელაციური ბაზა მონაცემს ცხრილებად (relation) ინახავს:

  • სვეტი (column, attribute) — ტიპიზებული ველი, მაგ. INTEGER, VARCHAR(32), TIMESTAMP, BOOLEAN, JSON;
  • მწკრივი (row, tuple) — ერთი ჩანაწერი.

ცხრილები ერთმანეთს გასაღებებით უკავშირდება. მონაცემი ნორმალიზებულია: ერთი ფაქტი ერთ ადგილას ინახება. შეკითხვები SQL ენით იწერება.

2. მარტივად რომ ავხსნათ. ცხრილი Excel-ის ფურცელს ჰგავს, მაგრამ უფრო მკაცრია. ყოველ სვეტს წინასწარ აქვს განსაზღვრული, რა შეიძლება ჩაიწეროს: თარიღის სვეტში თარიღი, რიცხვის სვეტში რიცხვი. და Excel-ისგან განსხვავებით, სახელი ასჯერ კი არ იწერება, არამედ ერთხელ, თავის ცხრილში. სხვაგან მხოლოდ მისი ნომერი დგას.

3. ჩვენს პროექტში. ძველ ცხრილში F სვეტში ამზომველის სახელი ოთხი სხვადასხვა ფორმით იწერებოდა: მხოლოდ სახელი; სახელი + ტაბულაცია + პირადი ნომერი; სახელი + რამდენიმე ჰარი + პირადი ნომერი; სახელი + ერთი ჰარი + პირადი ნომერი (qc-dashboard-main/HANDOFF.md, §6). შედეგად 661 ნედლი მნიშვნელობიდან 276 რეალური ადამიანი გამოვიდა. ✅ ახალ ბაზაში ადამიანი ერთხელ წერია users-ში, ოქმზე კი მხოლოდ user_id ინახება (item_people.user_id).

B.3 Primary key (პირველადი გასაღები)

1. ტექნიკური განმარტება. B.4 Foreign key და კავშირები

1. ტექნიკური განმარტება. Foreign key (FK) არის სვეტი, რომელიც სხვა ცხრილის primary key-ზე მიუთითებს, და ბაზა ამ კავშირის მთლიანობას იცავს (referential integrity): არარსებულ ჩანაწერზე მითითება შეუძლებელია. ON DELETE CASCADE მშობლის წაშლისას შვილსაც შლის, SET NULL მითითებას ასუფთავებს, ნაგულისხმევი RESTRICT / NO ACTION კი წაშლას კრძალავს. კავშირების ტიპები:

  • 1:N — ერთს ბევრი;
  • N:M — ბევრი-ბევრთან, შუალედური ცხრილით;
  • 1:1.

2. მარტივად რომ ავხსნათ. foreign key არის „ბმული“ ერთი ცხრილიდან მეორეზე. ოქმზე წერია „ოპერატორი №17“, და ბაზა არ დაუშვებს ოპერატორ №999-ის ჩაწერას, თუ ასეთი ადამიანი არ არსებობს.

1. ტექნიკური განმარტება. ინდექსი არის დამატებითი მონაცემთა სტრუქტურა (ჩვეულებრივ B-tree), რომელიც სვეტის მნიშვნელობით მწკრივის პოვნას ლოგარითმულ დროში უზრუნველყოფს და ამიტომ მთელი ცხრილის წაკითხვა (sequential scan) არ სჭირდება. ფასი: ყოველი ჩაწერა ინდექსსაც ანახლებს, და ინდექსი დისკზე ადგილს იკავებს. შედგენილი ინდექსი (a, b) ეხმარება ფილტრს a-ზე და a + b-ზე. რომელ ინდექსს იყენებს შეკითხვა, EXPLAIN / EXPLAIN ANALYZE აჩვენებს.

B.7 ტრანზაქცია და ACID

1. ტექნიკური განმარტება. ტრანზაქცია ოპერაციების ჯგუფია, რომელიც ACID თვისებებს აკმაყოფილებს:

  • Atomicity — ან ყველა ოპერაცია სრულდება, ან არცერთი;
  • Consistency — ტრანზაქციის შემდეგ ყველა შეზღუდვა დაცულია;
  • Isolation — ერთდროული ტრანზაქციები ერთმანეთის შუალედურ მდგომარეობას ვერ ხედავენ (დონეები: READ COMMITTED, REPEATABLE READ, SERIALIZABLE; PostgreSQL-ის ნაგულისხმევია READ COMMITTED);
  • Durability — COMMIT-ის შემდეგ მონაცემი ჩავარდნასაც უძლებს.

2. მარტივად რომ ავხსნათ. ტრანზაქცია არის „ყველაფერი ან არაფერი“. ბანკში ფულის გადარიცხვისას ერთ ანგარიშზე ფული მცირდება და მეორეზე იზრდება. თუ შუაში შუქი ჩაქრა, ფული არ უნდა გაქრეს. ორივე ნაბიჯი ერთად ხდება, ან არცერთი.

3. ჩვენს პროექტში. ✅ ოპერატორი „გაგზავნას“ აჭერს. ერთ ტრანზაქციაში ხდება:

მარტივად: ეს ბრძანებები ერთად ცვლის ოქმის სტატუსს, ხარვეზის კოდებს და წერს ისტორიაში, „ვინ და როდის გაგზავნა“. თუ რომელიმე ნაბიჯი ჩავარდა, არცერთი ცვლილება არ შეინახება, და ოქმი „ნახევრად გაგზავნილი“ ვერ დარჩება.

4. რატომ. ისტორია და მდგომარეობა არასოდეს უნდა დაშორდეს ერთმანეთს. სტატუსი შეიცვალა, ისტორიაში კი არ ჩაიწერა — ასეთი რამ დაუშვებელია.

5. კულისებში. SQLAlchemy-ის Session ტრანზაქციას პირველ შეკითხვაზე ხსნის. db.commit() მას ადასტურებს, შეცდომისას db.rollback() კი აუქმებს (routes/items.action). ✅ განაწილების დადასტურებაც ასეა: ათასობით ოქმი ერთ ტრანზაქციაში იქმნება (service.confirm).

6. რა შეიძლება აირიოს. ძალიან გრძელი ტრანზაქცია ბლოკავს სხვებს. 💡 დიდი განაწილება PostgreSQL-ზე უნდა გაიზომოს.

7. IT იკითხავს. „არათანმიმდევრული მდგომარეობა როგორ გამოირიცხება?“

8. პასუხი. „ყოველი მოქმედება ერთი ტრანზაქციაა: მდგომარეობის ცვლილება, კოდები, ისტორია და ფაილის ჩანაწერი ერთად ინახება ან ერთად უქმდება. ამას ემატება CHECK შეზღუდვები დასაშვებ მდგომარეობებზე.“

B.8 ერთდროული ცვლილება: ბლოკირება და ვერსია

1. ტექნიკური განმარტება. ერთი ჩანაწერის ერთდროული ცვლილების კლასიკური პრობლემაა „lost update“: ორივე კითხულობს ვერსია 7-ს, ორივე წერს, და მეორე პირველის ცვლილებას „გადაწერს“. გამოსავალი ორია:

  • პესიმისტური ბლოკირება — SELECT … FOR UPDATE მწკრივს ტრანზაქციის ბოლომდე კეტავს;
  • ოპტიმისტური ბლოკირება — ჩანაწერს version სვეტი აქვს, და განახლება მხოლოდ მაშინ სრულდება, თუ ვერსია არ შეცვლილა:
UPDATE qc_items SET …, version = version + 1
 WHERE id = 4512 AND version = 7;
-- თუ განახლდა 0 მწკრივი → ვიღაცამ უკვე შეცვალა → მომხმარებელს ვეუბნებით

2. მარტივად რომ ავხსნათ. თითო ოქმს „მრიცხველი“ აქვს. როცა ბარათს ხსნი, გახსოვს, რომ მრიცხველი 7-ზეა. როცა „გაგზავნას“ აჭერ, სისტემა ამოწმებს, ისევ 7-ზეა თუ არა. თუ ამასობაში ვინმემ უკვე შეცვალა და 8 გახდა, შენი ცვლილება არ შეინახება და გეტყვის: „ჩანაწერი სხვამ შეცვალა, გადახედე“.

3. ჩვენს პროექტში.

  • ✅ qc_items.version. ფორმა მას ატარებს, workflow.apply() კი ადარებს: if str(v) != str(item.version): raise ConflictError;
  • ✅ ველზე ორი ამზომველის ერთდროული პასუხისას მეორე იღებს შეტყობინებას: „ამ ოქმზე პასუხი უკვე გაგზავნა X-მა (დრო) — ერთ კოდზე ერთი პასუხი იგზავნება“ (routes/items.action);
  • ✅ დამატებით, „ახლა ხსნის“ ნიშანი ადამიანებს წინასწარ აფრთხილებს.
  • ⚠️ G5: შედარება აპლიკაციაში ხდება, ხოლო UPDATE WHERE version = ?-ის გარეშე იგზავნება. SQLite ჩაწერებს რიგრიგობით ასრულებს, ამიტომ პრაქტიკული რისკი მცირეა. PostgreSQL-ზე რამდენიმე worker-ით ორი ზუსტად ერთდროული მოთხოვნა ორივე გაივლის. 💡 გამოსავალი: SQLAlchemy version_id_col (ის ზუსტად WHERE version = ?-ს ამატებს) ან SELECT … FOR UPDATE.

4. რატომ. ბიზნეს-წესია: „ერთ კოდზე ერთი პასუხი“, და „პირველი გაგზავნილი ითვლება“.

5. კულისებში. PostgreSQL-ის MVCC-ში ყოველი ტრანზაქცია მონაცემის „სნეპშოტს“ ხედავს. ერთი მწკრივის ერთდროულ UPDATE-ს ბაზა რიგში აყენებს: მეორე პირველის დასრულებას ელოდება, მერე კი WHERE version = 7 პირობას თავიდან ამოწმებს. ის აღარ სრულდება, და შედეგად 0 მწკრივი განახლდება.

6. რა შეიძლება აირიოს. ფორმამ version არ გამოაგზავნა (მაგ. API კლიენტმა). ⚠️ დღეს ასეთ შემთხვევაში შემოწმება გამოტოვდება. 💡 სავალდებულო უნდა გახდეს.

7. IT იკითხავს. „ორი ადამიანი ერთ ჩანაწერს რომ ცვლიდეს?“

8. პასუხი. „ოპტიმისტური ბლოკირება გვაქვს ვერსიის ნომრით: მეორე ცვლილება უარყოფილია და ადამიანი ხედავს, ვინ და როდის გააკეთა პირველი. PostgreSQL-ზე გადასვლისას შემოწმებას ბაზის დონეზე გადავიტანთ, UPDATE … WHERE version = ?-ით.“

B.9 View (წარმოდგენა)

1. ტექნიკური განმარტება. View არის შენახული SELECT შეკითხვა, რომელიც ვირტუალური ცხრილივით გამოიყენება. მისი გამოყენებით:

  • მომხმარებელს მხოლოდ საჭირო სვეტები და მწკრივები ეჩვენება (უსაფრთხოება: GRANT SELECT მხოლოდ view-ზე);
  • რთული join-ები იმალება;
  • შიდა სტრუქტურის ცვლილება მომხმარებელს არ ეხება, თუ view უცვლელია (სტაბილური ინტერფეისი).

Materialized view შედეგს ფიზიკურად ინახავს და REFRESH-ით ახლდება. ის სწრაფია, მაგრამ შეიძლება მოძველდეს.

2. მარტივად რომ ავხსნათ. view არის „ფანჯარა“ დიდ ცხრილზე: ჩანს მხოლოდ ის, რისი დანახვაც გვინდა. IT-ს თავისი სისტემის „კარის გაღება“ არ სჭირდება, მხოლოდ პატარა ფანჯარას გვიჭრის, საიდანაც ჩვენთვის საჭირო 7 სვეტი ჩანს.

3. ჩვენს პროექტში. 💡 IT-სთვის ჩვენი პირველი რეკომენდაცია REGFIELDALL-სა და სპორადულისთვის სწორედ view-ია (docs/IT_REQUEST.md §3). მაგალითი (ილუსტრაცია; ცხრილისა და სქემის სახელები IT-ის სისტემაში ❓ უცნობია):

-- IT-ის მხარეს, მათ ბაზაში
CREATE VIEW qc_export.v_regfield_for_qc AS
SELECT fld_paper_id, cadcode, mox_create_date, fld_status_name,
       oqmi_creator, moxaz_creator, is_last
  FROM <regfieldall_ცხრილი>
 WHERE mox_create_date >= DATE '2026-01-01';

CREATE ROLE qc_reader LOGIN PASSWORD '…';
GRANT USAGE  ON SCHEMA qc_export TO qc_reader;
GRANT SELECT ON qc_export.v_regfield_for_qc TO qc_reader;   -- სხვა არაფერი

მარტივად: პირველი ბრძანება ქმნის „ფანჯარას“, სადაც მხოლოდ 7 სვეტი ჩანს, და მხოლოდ 2026 წლიდან. დანარჩენი ორი ქმნის ცალკე მომხმარებელს, რომელსაც მხოლოდ ამ ფანჯრის წაკითხვის უფლება აქვს. ის ვერაფერს შეცვლის და სხვა ცხრილს ვერ დაინახავს.

4. რატომ. უსაფრთხოებისა და სტაბილურობისთვის საუკეთესო ბალანსია: IT აკონტროლებს, რას ვხედავთ, ჩვენ კი ყოველთვის ახალ მონაცემს ვიღებთ.

5. კულისებში. view-ზე შეკითხვისას ბაზა view-ის განმარტებას ჩვენს შეკითხვასთან აერთიანებს და ძირითადი ცხრილის ინდექსებს იყენებს.

6. რა შეიძლება აირიოს.

  • view-ზე დიდი შეკითხვა წყარო სისტემას ტვირთავს. ამიტომ ღამით ვკითხულობთ და ჩვენთან ვინახავთ (C.9);
  • IT view-ის სტრუქტურას ცვლის და ჩვენი იმპორტი ტყდება. საჭიროა შეთანხმებული „კონტრაქტი“.

7. IT იკითხავს. „რატომ view და არა API?“

8. პასუხი. „view ყველაზე ნაკლებ სამუშაოს მოითხოვს თქვენგან: ერთი CREATE VIEW და ერთი read-only მომხმარებელი. API ასევე გამოდგება, თუ უკვე გაქვთ. ფაილიც მისაღებია, თუ ბაზაზე წვდომა თქვენი პოლიტიკით აკრძალულია.“

B.10 მიგრაცია (სქემის ცვლილება)

1. ტექნიკური განმარტება. სქემის მიგრაცია არის ბაზის სტრუქტურის ვერსიირებული, თანმიმდევრული ცვლილება: სვეტის დამატება, ინდექსი, ცხრილის გაყოფა. ინსტრუმენტი (Python-ში Alembic) ინახავს მიგრაციის ფაილებს (upgrade() / downgrade()) და ბაზაში წერს, რომელი ვერსიაა ბოლოს გამოყენებული (alembic_version ცხრილი). მონაცემის მიგრაცია სხვა რამეა: ძველი სისტემიდან მონაცემის გადატანა (თავი F).

2. მარტივად რომ ავხსნათ. მიგრაცია ბაზის „რემონტის გეგმაა“, ნაბიჯ-ნაბიჯ ჩაწერილი: „ვერსია 3: ოქმს დაემატოს ველი ‚ვადა‘“. ყოველ სერვერზე ეს გეგმა ერთნაირად სრულდება, და ყოველთვის ცნობილია, რომელ ვერსიაზეა ბაზა.

3. ჩვენს პროექტში.

  • ⚠️ G2: მიგრაციის ინსტრუმენტი არ არის. ცხრილები Base.metadata.create_all(engine)-ით იქმნება აპლიკაციის ჩართვისას (app/main.py). create_all ახალ ცხრილს ქმნის, მაგრამ არსებულს არ ცვლის: ახალი სვეტი არსებულ ცხრილს არ დაემატება;
  • ✅ ჩვენს სხვა პროექტს (Pre-QC hosted) უკვე აქვს Alembic (hosted/alembic.ini). გამოცდილება გვაქვს. იქ აღმოჩენილი ხაფანგი: alembic.ini მხოლოდ ASCII უნდა იყოს.

4. რატომ. საწარმოოში ბაზას ვერ წავშლით და ვერ ავაწყობთ თავიდან. ყოველი ცვლილება უსაფრთხოდ, ბექაპით და დაბრუნების შესაძლებლობით უნდა მოხდეს.

5. კულისებში. Alembic-ის მიგრაციის მაგალითი:

  • ანალიტიკის როლი (საჭიროებისას) — მხოლოდ SELECT view-ებზე.

წყარო სისტემებზე ჩვენი როლი მხოლოდ SELECT-ს იღებს, მხოლოდ view-ზე.

2. მარტივად რომ ავხსნათ. თითოეულს იმდენი გასაღები აქვს, რამდენიც სჭირდება. საიტს „კარადის“ გახსნა და ქაღალდის ჩადება შეუძლია, მაგრამ კარადის დანგრევა — არა. ჩვენს გასაღებს IT-ის სისტემაში მხოლოდ ერთი ფანჯრის გაღება შეუძლია, და მხოლოდ საყურებლად.

3. ჩვენს პროექტში. 💡 შეთავაზება (PostgreSQL):

GRANT USAGE ON SCHEMA public TO qc_app;

მარტივად: ვქმნით ორ „ანგარიშს“ ბაზაში: ერთი მხოლოდ განახლებისას გამოიყენება და სტრუქტურას ცვლის, მეორეს საიტი იყენებს ყოველდღიურად. ბოლო ბრძანება ისტორიის ცხრილს „ბეტონში ასხამს“: საიტს მასში მხოლოდ ახლის დამატება შეუძლია, შეცვლა და წაშლა კი არა.

⚠️ ბოლო ხაზამდე უნდა შევამოწმოთ, რომ საწარმოოს არცერთი კოდის გზა qc_events-ს არ ცვლის. ძველი მონაცემის ხელახალი იმპორტი (legacy_import) მას შლის, ამიტომ ის მიგრაციის როლით უნდა გაეშვას. Pre-QC hosted-ში append-only ბაზის ტრიგერითაც არის დაცული. 💡 იგივე ხერხი ჩვენთვისაც გამოდგება.

4. რატომ. თუ აპლიკაცია გატყდა (მაგ. SQL injection-ის მცდელობა), ზიანი შეზღუდულია.

B.17 როგორ ესაუბრება ჩვენი საიტი ბაზას

1. ტექნიკური განმარტება. აპლიკაცია ბაზას ORM-ით (SQLAlchemy 2) უკავშირდება:

  • Engine კავშირების აუზს მართავს;
  • Session ერთი სამუშაო ერთეულია (unit of work), ჩვეულებრივ ერთი HTTP მოთხოვნა;
  • მოდელები Python კლასებია, რომლებიც ცხრილებს შეესაბამება;
  • შეკითხვები Python-ში იწერება, და SQLAlchemy მათ კონკრეტული ბაზის SQL დიალექტად თარგმნის.

2. მარტივად რომ ავხსნათ. ჩვენი კოდი ბაზას პირდაპირ SQL-ით, როგორც წესი, არ ელაპარაკება. ის „თარჯიმანს“ (SQLAlchemy-ს) ეუბნება, მაგალითად: „მომეცი ამ ოპერატორის გასავლელი ოქმები“. თარჯიმანი ამას SQL-ად თარგმნის, იმ ბაზის ენაზე, რომელიც ახლა გვაქვს. ამიტომ SQLite-დან PostgreSQL-ზე გადასვლისას კოდის უმეტესობა არ იცვლება.

C. API და გარე მონაცემი

C.1 HTTP — როგორ ესაუბრება ბრაუზერი სერვერს

1. ტექნიკური განმარტება. HTTP არის მოთხოვნა-პასუხის (request/response) პროტოკოლი TCP-ზე. HTTPS იგივეა, ოღონდ TLS-ით დაშიფრული. მოთხოვნა შედგება:

  • მეთოდისგან:
    • GET — წაკითხვა, მდგომარეობას არ ცვლის;
    • POST — შექმნა ან მოქმედება;
    • PUT / PATCH — განახლება;
    • DELETE;
  • ბილიკისგან (/items/4512) და query string-ისგან (?tab=todo);
  • თავსართებისგან (headers: Cookie, Origin, Content-Type, Authorization);
  • სხეულისგან (body: ფორმა ან JSON).

პასუხი შედგება სტატუს-კოდის, თავსართებისა და სხეულისგან.

კოდი მნიშვნელობა ჩვენთან ✅
200 OK გვერდი / JSON
303 See Other — გადამისამართება ყოველი მოქმედების შემდეგ (POST → GET), რომ გვერდის განახლებამ მოქმედება არ გაიმეოროს
401 ავთენტიფიკაცია საჭიროა /api/* შესვლის გარეშე → {"error": "login_required"}
403 აკრძალულია როლს ეს გვერდი არ ეკუთვნის (მაგ. ოპერატორი → /admin)
404 ვერ მოიძებნა სხვისი ჩანაწერიც (განზრახ, D.9)
413 ძალიან დიდი მოთხოვნა proxy-ს ლიმიტი (საწარმოოში)
500 სერვერის შეცდომა კოდის შეცდომა
502 / 503 / 504 proxy ვერ უკავშირდება აპლიკაციას / გადატვირთულია / timeout აპლიკაცია გაჩერებულია ან ნელია

2. მარტივად რომ ავხსნათ. HTTP წერილების გაცვლაა. ბრაუზერი სერვერს წერს: „მომეცი ოქმი 4512“ (GET) ან „ამ ოქმზე ვაგზავნი პასუხს“ (POST). სერვერი პასუხობს ნომრით, რომელიც გვეუბნება, რა მოხდა: 200 — „აი, ინებე“, 404 — „ასეთი არ არის“, 403 — „შენ არ შეგიძლია“, 500 — „ჩემთან რაღაც გაფუჭდა“.

3. ჩვენს პროექტში. ✅

  • მოქმედებები POST-ით ხდება და პასუხად 303 მოდის (routes/common.redirect);
  • Cache-Control: no-store ედება /api/*-სა და /items/*-ს (app/main.py), რომ ბრაუზერმა ან proxy-მ ოქმის მონაცემი ქეშში არ შეინახოს.

4. რატომ. IT-ის ლოგებსა და შეცდომის აღწერებში სწორედ ეს კოდები ჩანს. „502“ პრობლემას proxy-სა და აპლიკაციას შორის აჩვენებს, „500“ — ჩვენს კოდში.

5. კულისებში. მოქმედების ფორმა გაიგზავნება POST /items/4512/action-ზე, Content-Type: multipart/form-data-თი (ფოტოს ჩათვლით), cookie-თი და Origin თავსართით.

6. რა შეიძლება აირიოს. GET-ით მდგომარეობის შეცვლა: ბმულზე დაჭერამ ან სხვა საიტის <img>-მა მოქმედება გამოიწვია. ✅ ჩვენთან ყველა ცვლილება POST-ით ხდება, logout-ის ჩათვლით.

7. IT იკითხავს. „რომელი მეთოდები და ბილიკები უნდა დაუშვას proxy-მ / WAF-მა?“

8. პასუხი. „GET და POST, ერთი დომენის ყველა ბილიკზე; multipart ატვირთვა 10 MB-მდე. სრული სია OpenAPI-შია (/docs).“

C.2 JSON

1. ტექნიკური განმარტება. JSON (JavaScript Object Notation) არის ტექსტური ფორმატი სტრუქტურირებული მონაცემისთვის. ელემენტებია ობიექტი {"key": value}, მასივი […], სტრიქონი, რიცხვი, true/false, null. კოდირება UTF-8-ია, ამიტომ ქართული ტექსტი პირდაპირ იწერება.

2. მარტივად რომ ავხსნათ. JSON არის „ანკეტა“, რომელსაც კომპიუტერები ერთმანეთს უგზავნიან: ველის სახელი და მნიშვნელობა, მკაცრი წესით, რომ ორივე მხარემ ერთნაირად წაიკითხოს.

3. ჩვენს პროექტში. ✅

  • ჩვენი API JSON-ს აბრუნებს;
  • Apps Script-იდან მონაცემი JSON-ად მოდის (data/raw/*.json);
  • WFS პასუხს GeoJSON-ად ვითხოვთ (outputFormat=application/json);
  • ბაზაშიც რამდენიმე სვეტი JSON-ია (settings.value, distribution_runs.params, legacy_extra).

4–8. იხ. C.3, სადაც JSON-ის რეალური მაგალითია.

C.3 API და REST — ჩვენი API-ს მაგალითები

1. ტექნიკური განმარტება. API (Application Programming Interface) არის შეთანხმებული წესი, რომლითაც ერთი პროგრამა მეორეს მიმართავს. REST HTTP-ზე დაფუძნებული სტილია:

  • რესურსები ბილიკებია (/api/items/{id});
  • მოქმედება HTTP მეთოდით გამოიხატება;
  • მდგომარეობა სერვერზე არ ინახება მოთხოვნებს შორის (stateless), ავთენტიფიკაციის გარდა;
  • პასუხი ჩვეულებრივ JSON-ია.

OpenAPI API-ს მანქანურად წაკითხვადი აღწერაა. FastAPI მას ავტომატურად ქმნის (/openapi.json, /docs).

2. მარტივად რომ ავხსნათ. API არის „სარკმელი“ პროგრამებისთვის. ადამიანი საიტს ღილაკებით იყენებს; სხვა პროგრამა, მაგალითად Pre-QC ან სააგენტოს სხვა სისტემა, იგივე ინფორმაციას API-ით იღებს: ზუსტად განსაზღვრული კითხვით და ზუსტად განსაზღვრული ფორმის პასუხით.

C.4 WFS — რუკის ობიექტების წაკითხვა

1. ტექნიკური განმარტება. WFS (Web Feature Service) არის OGC-ის სტანდარტი გეოგრაფიული ობიექტების (feature) HTTP-ით მისაღებად, გეომეტრიითა და ატრიბუტებით. მთავარი ოპერაციებია GetCapabilities, DescribeFeatureType და GetFeature. ფილტრაციისთვის გამოიყენება OGC Filter ან (GeoServer-ზე) CQL. WMS სხვა რამეა: ის რუკის სურათს აბრუნებს და არა ობიექტებს.

2. მარტივად რომ ავხსნათ. WFS რუკის „API-ა“. ვეკითხებით: „მომეცი ნაკვეთი, რომლის საკადასტრო კოდია ესა და ეს“, და ვიღებთ მის ზუსტ საზღვრებს (კოორდინატებს) და მონაცემებს. ამით პროგრამა ამოწმებს, მაგალითად, ნაკვეთი მეზობელს ხომ არ ეფარება.

3. ჩვენს პროექტში. ✅ WFS-ს Pre-QC Validator იყენებს (pre-qc-validator-master/app/wfs.py); პლატფორმა დღეს WFS-ს არ იყენებს. მოთხოვნის სტრუქტურა (რეალური პარამეტრები, ფილტრის მნიშვნელობა ილუსტრაციაა):

    &propertyName=SHAPE,TAG,ZONE,SECTOR,CADCODE,FUNCTION,CATEGORY,GFLD_PARCEL_ID,...

Authorization: Basic <მომხმარებელი:პაროლი, base64>

{"type": "FeatureCollection",

               "geometry": {"type": "Polygon", "coordinates": [[[480123.4, 4620456.7], …]]},

4. რატომ. Pre-QC-ის GIS-შემოწმებები (ფართობი, გადაფარვა, მეზობლები) ამაზე დგას.

  • graceful degradation — წყაროს ჩავარდნა მთელ სისტემას არ აჩერებს;

D.2 HTTPS, TLS და სერტიფიკატი

1. ტექნიკური განმარტება. TLS (Transport Layer Security) არის შიფრაციის პროტოკოლი. HTTPS = HTTP TLS-ზე. TLS უზრუნველყოფს:

  • კონფიდენციალურობას — დაშიფვრა;
  • მთლიანობას — ცვლილების აღმოჩენა;
  • სერვერის ავთენტიფიკაციას — სერტიფიკატით.

სერტიფიკატს სანდო ცენტრი (CA) გასცემს: საჯარო CA (Let's Encrypt, კომერციული) ან ორგანიზაციის შიდა CA. შიდა CA-ს სერტიფიკატს მხოლოდ ის მოწყობილობები ენდობა, რომლებზეც შიდა root CA დაყენებულია. ეს ტელეფონებზე ხშირად პრობლემაა. რეკომენდებულია TLS 1.2+, სასურველია 1.3.

2. მარტივად რომ ავხსნათ. HTTPS „დალუქული კონვერტია“. გზაში ვერავინ წაიკითხავს და ვერ შეცვლის. სერტიფიკატი კი „პირადობის მოწმობაა“, რომელიც ამტკიცებს: ეს ნამდვილად სააგენტოს საიტია და არა ყალბი.

3. ჩვენს პროექტში.

  • ✅ დღეს HTTPS არ არის (localhost / LAN);
  • ✅ cookie-ს Secure ნიშანი HTTPS-ზე ჩაირთვება (Google-ით შესვლისას), მაგრამ proxy-ს გამო იხ. G4;
  • 💡 საწარმოოში HTTPS სავალდებულოა.

4. რატომ.

  • Google OAuth redirect URI-ს HTTPS-ით მოითხოვს (localhost-ის გარდა);
  • სესიის cookie, პაროლები და QC მონაცემი ღია ტექსტით ქსელში არ უნდა მოძრაობდეს, განსაკუთრებით ტელეფონიდან, საჯარო ქსელით.

5. კულისებში. TLS-ის დაწყებისას (handshake) სერვერი სერტიფიკატს აგზავნის, ბრაუზერი ამოწმებს სახელს, ვადას და ხელმოწერის ჯაჭვს, შემდეგ კი სესიის გასაღები იქმნება. 💡 TLS proxy-ზე სრულდება (A.6).

6. რა შეიძლება აირიოს.

  • სერტიფიკატის ვადა ამოიწურა (საჭიროა ავტომატური განახლება ან კალენდარი);
  • ტელეფონი შიდა CA-ს არ ენდობა და „საიტი სახიფათოა“-ს წერს;

D.6 სესია და cookie

1. ტექნიკური განმარტება. შესვლის შემდეგ სერვერი სესიას ქმნის და ბრაუზერს cookie-ს აძლევს. ორი მიდგომა არსებობს:

  • (ა) სერვერის მხარის სესია — cookie-ში მხოლოდ იდენტიფიკატორია, მონაცემი ბაზაში ინახება. მყისიერი გაუქმება შესაძლებელია;
  • (ბ) თვითკმარი token (JWT) — ყველაფერი token-შია. გაუქმება რთულია.

cookie-ს ნიშნები:

  • HttpOnly — JavaScript ვერ კითხულობს (XSS-ისგან დაცვა);
  • Secure — მხოლოდ HTTPS-ით იგზავნება;

D.9 CSRF

1. ტექნიკური განმარტება. CSRF (Cross-Site Request Forgery): მავნე საიტი მომხმარებლის ბრაუზერს აიძულებს, ჩვენს საიტზე მოთხოვნა გააგზავნოს. ბრაუზერი cookie-ს ავტომატურად ურთავს, ამიტომ მოთხოვნა „ავთენტიფიცირებულად“ გამოიყურება. დაცვის ხერხები:

  • SameSite cookie;
  • Origin / Referer თავსართის შემოწმება;
  • CSRF token ფორმაში.

2. მარტივად რომ ავხსნათ. სხვა საიტს შეუძლია, შენი ბრაუზერის სახელით ჩვენს საიტზე „ღილაკი დააჭიროს“, რადგან ბრაუზერი შენს სამაჯურს ავტომატურად აჩვენებს. დაცვა: სერვერი ამოწმებს, საიდან მოვიდა მოთხოვნა, და თუ სხვა საიტიდან, უარყოფს.

3. ჩვენს პროექტში.

  • ✅ security.same_origin(): ყველა მდგომარეობის შემცვლელ POST-ზე Origin (ან Referer) უნდა ემთხვეოდეს Host-ს. ტესტი: test_cross_site_post_is_rejected;
  • ✅ SameSite=Lax;
  • ⚠️ G8: თუ ორივე თავსართი აკლია, მოთხოვნა გადის. 💡 CSRF token-ის დამატება საწარმოომდე (უკვე წერია ARCHITECTURE.md §11-ში).

D.16 უსაფრთხოების თავსართები

✅ app/main.py ყველა პასუხს ამატებს:

  • X-Content-Type-Options: nosniff — ბრაუზერი ფაილის ტიპს არ „გამოიცნობს“;

💡 დასამატებელია:

  • Strict-Transport-Security (HSTS), proxy-ზე;
  • Content-Security-Policy მთელ საიტზე (მეილის ნახვის გვერდს CSP უკვე აქვს: /admin/emails/{id}).
