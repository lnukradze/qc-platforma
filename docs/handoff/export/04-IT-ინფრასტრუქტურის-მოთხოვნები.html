2. თითო მოთხოვნა დეტალურად

R1. ვირტუალური სერვერი (VM)

  1. რა გვჭირდება: ერთი VM. 💡 საწყისი შეფასება: 4 vCPU, 8 GB RAM, 100 GB SSD, PostgreSQL-ის ჩათვლით, თუ ბაზა იმავე VM-ზეა. ბაზის ცალკე სერვერზე განთავსებისას აპლიკაციის VM-ს 2 vCPU და 4 GB RAM ეყოფა (შეფასება).
  2. რატომ: აპლიკაცია (uvicorn, 2–4 worker), ფონური ამოცანები (ღამის იმპორტი, მეილის რიგი), reverse proxy (თუ VM-ზეა) და PostgreSQL ერთად. შეფასების საფუძველი:
    • ≈ 300 მომხმარებელი, ერთდროულად ≈ 40 (IT_REQUEST.md-ის შეფასება);
    • ✅ დღევანდელი ბაზა 94 MB-ია, 44 159 შემთხვევაზე;
    • ✅ სტატისტიკა SQLite-ზე 2–3 წმ-ს იღებს;
    • ✅ REGFIELDALL-ის ასლი ≈ 1 GB-ია.
  3. დამოკიდებულია: ყველაფერი.
  4. M, P1.
  5. ალტერნატივები:
    • ადგილი არსებულ აპლიკაციის სერვერზე ან კონტეინერის პლატფორმაზე (Docker host, Kubernetes namespace);
    • მცირე რესურსით დაწყება და გაზრდა გაზომვის შემდეგ.
  6. თუ ვერ მოგვცემს: პლატფორმა ვერ გაიშვება. დარჩება პროტოტიპი ერთ კომპიუტერზე, რაც საწარმოოსთვის მიუღებელია (სახელმძღვანელო A.2).
  7. 🗣 მარტივად: „ერთი ვირტუალური სერვერი გვჭირდება, საშუალო ოფისის კომპიუტერის სიმძლავრის. ეს შეფასებაა: პილოტზე გავზომავთ და საჭიროებისას შევამცირებთ ან გავზრდით.“

R2. ოპერაციული სისტემა და runtime

  1. რა გვჭირდება: Linux (Ubuntu LTS / RHEL-ის ოჯახი) ან Windows Server. Python ≥ 3.12, ვირტუალური გარემოთი; ან Docker Engine, თუ კონტეინერი აირჩევა. სააგენტოს root CA-ს სერტიფიკატი OS-ის საცავში (კორპორატიული TLS-ისთვის). Linux-ზე: systemd სერვისი; Windows-ზე: Windows Service ან კონტეინერი.
  2. რატომ:
    • ✅ კოდი OS-დამოუკიდებელია (pathlib, QCP_*);
    • ✅ truststore OS-ის სერტიფიკატების საცავს იყენებს, ამიტომ შიდა CA იქ უნდა იყოს. თორემ Google OAuth-ზე და SMTP TLS-ზე კავშირი ჩავარდება;
    • ✅ ტესტირებულია Python 3.14.5-ზე, მოთხოვნა ≥ 3.12.
  3. დამოკიდებულია: აპლიკაციის გაშვება.
  4. M, P1.
  5. ალტერნატივები: ჩვენ ვამზადებთ Docker image-ს, IT კი მხოლოდ კონტეინერის host-ს გვაძლევს. ⚠️ Dockerfile ჯერ არ არსებობს — ეს ჩვენი სამუშაოა.
  6. თუ ვერ მოგვცემს: —
  7. 🗣 მარტივად: „თქვენი სტანდარტული ოპერაციული სისტემა გამოგვადგება. პროგრამა ორივეზე მუშაობს. Docker-ის „ყუთში“ თუ მოგაწვდით, ინსტალაციაც მარტივი იქნება.“

R3. PostgreSQL ბაზა

  1. რა გვჭირდება: PostgreSQL 14+ (💡 სასურველია 16), ცალკე ბაზა (მაგ. qc), UTF-8 კოდირებით. ორი მომხმარებელი:
    • qc_app — აპლიკაცია: მონაცემის წაკითხვა და ჩაწერა, სქემის შეცვლის გარეშე;
    • qc_migrator — სქემის მფლობელი, მიგრაციისთვის. superuser არ გვჭირდება. კავშირი მხოლოდ აპლიკაციის სერვერიდან; TLS, თუ ბაზა სხვა VM-ზეა.
  2. რატომ:
    • ერთდროული ჩაწერა (MVCC);
    • ტრანზაქციები და შეზღუდვები;
    • ბექაპი / PITR;
    • უფლებების მართვა. SQLite (✅ პროტოტიპი) ერთ მწერალს უშვებს და ქსელურ წვდომას არ იძლევა (სახელმძღვანელო B.11).
  3. დამოკიდებულია: ყველა მონაცემი — ოქმები, ისტორია, მომხმარებლები, სესიები.
  4. M, P1.
  5. ალტერნატივები: Microsoft SQL Server, თუ ეს სააგენტოს სავალდებულო სტანდარტია. ⚠️ ამ შემთხვევაში ჩვენ ტესტირება და დიალექტის განსხვავებების გასწორება გვიწევს (JSON სვეტები, collation, თარიღები).
  6. თუ ვერ მოგვცემს: სერვერული ბაზის გარეშე საწარმოო გაშვება შეუძლებელია.
  7. 🗣 მარტივად: „ბაზა ცენტრალური, დაცული „კარადაა“, სადაც საიტი ყველა ჩანაწერს ინახავს. თქვენს არსებულ DB სერვერზე ცალკე ბაზაც საკმარისია. ახალი სერვერი სავალდებულო არ არის.“

⚠️ ჩვენი მხრიდან (G1, G2): PostgreSQL-ის დრაივერი ჯერ არ არის დაყენებული და ტესტი არ ჩატარებულა; მიგრაციის ინსტრუმენტი (Alembic) დასამატებელია. 💡 სატესტო PostgreSQL ადრე რომ მივიღოთ, ამ სამუშაოს პარალელურად გავაკეთებთ.
