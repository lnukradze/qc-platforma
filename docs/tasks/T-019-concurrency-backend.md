## 1. ბრიფი — lead

**მიზანი (P0):** წესი — „ერთ კოდზე ერთი პასუხი; პირველი პასუხი ითვლება“ (`docs/OPEN_QUESTIONS.md`, „ორი ამზომველი ერთად“). T-009-მა (E-06) დაადასტურა,
რომ ორი ერთდროული პასუხი **ორივე** ინახება: ვერსიის შემოწმება (`workflow.py:235`) წაკითხვასა და ჩაწერას შორის ატომური არ არის.
ერთიანი სურათი — `docs/reports/STAGE-1-SUMMARY.md`, P0-2.

**შედის:**
1. **ატომური ვერსია** — ყოველი ქმედება, რომელიც მდგომარეობას / სტატუსს ცვლის: ჩაწერა ერთი `UPDATE qc_items … WHERE id = :id AND version = :v` (ან SQLAlchemy
   `version_id_col`), შეცვლილი მწკრივი 0 → `ConflictError` (არსებული შეტყობინებით „ამ ოქმზე პასუხი უკვე გაგზავნა …“). SQLite-ზეც და PostgreSQL-ზეც.
   `version` ფორმაში **სავალდებულოა** მდგომარეობის შემცვლელ ქმედებებზე (T-010, S-09).
2. **კომენტარი** — B-11: ორჯერ დაჭერა / ორი ჩანართი → ერთი კომენტარი და ერთი მეილი (ერთჯერადი token ფორმაში ან „იგივე ტექსტი + ავტორი ბოლო 60 წმ-ში“ → არ იქმნება).
   B-12: კომენტარი და QC მენეჯერის შეფასება `version`-ს **არ** ზრდის (კონფლიქტი მხოლოდ მდგომარეობის / სტატუსის ცვლილებაზე).
3. რეგრესიის ტესტი **ნამდვილი პარალელით** (ორი ნაკადი / ორი სესია, ერთი საწყისი `version`, ერთდროული POST) — 20 გამეორება, ყოველთვის ზუსტად ერთი წარმატება.

**არ შედის:** შაბლონები (ui-ს ფორმის ველი, თუ token სჭირდება — „სხვა როლებისგან სჭირდება“ commit-ში); სხვა სამუშაო წესები — T-021.

**ფაილები (ზონა):** `app/workflow.py`, `app/routes/items.py`, `app/services/notify.py`, `tests/test_concurrency.py` (ახალი — ნებადართული გამონაკლისი).

**დასრულების პირობა** (ტესტირებადი):

**ჩაბარებისას შევამოწმებ:** პარალელური ტესტი ჩემთანაც 20 / 20; ისტორია — ერთი პასუხი.

### წასაკითხი წყაროები და მიმდინარე პრობლემა

- `app/workflow.py:apply()`: `form.get("version")` მხოლოდ არსებობისას შედარდება წაკითხულ `item.version`-ს; ეს Python შედარება არ არის ატომური. `_event()`, `_set_codes()`, `_set_surveyors()` და `save_files()` გზაზე flush-ებია, ბოლოს კი ყველა ქმედებაზე `item.version += 1` ხდება. ტრანზაქციის დაცვა ყველა ამ გვერდით ეფექტს უნდა მოიცავდეს.

- `app/routes/qc.py:bulk_send()`: `send`-ს `version`-ის გარეშე იძახებს; `WorkflowError`-ს იჭერს და ციკლს აგრძელებს; ბოლოს ერთი commit-ია. ადრინდელი flush-ების გამო უარყოფილი მოქმედების ნაწილობრივი ცვლილებების კომიტის რისკი ცალკე შესაფასებელია. UI-დან ღილაკის მოცილება endpoint-ს არ აუქმებს.

### პასუხისმგებლობის საზღვრები

- ნებადართული განხორციელება: `app/workflow.py`, `app/routes/items.py`, `app/services/notify.py`, ახალი `tests/test_concurrency.py` (ბრიფის პირდაპირი გამონაკლისი). ამოცანის დოკუმენტის ნაწილებს backend არ ცვლის.
- `app/models.py`, `app/domain.py`, `app/config.py`, ახალი მოდელი/ველი/unique constraint/მიგრაცია — lead-ისაა. თუ არჩეულ მექანიზმს `version_id_col` ან token-ის მდგრადი საცავი სჭირდება, წარმოადგინე ზუსტი კონტრაქტის საჭიროება და შესაბამის ცვლილებაზე lead-ს დაელოდე; თვითნებურად schema არ შეცვალო.
- UI შაბლონები არ შეცვალო. თუ token აირჩევა, სხვა როლებისგან სჭირდება — ui: ბარათის კონტექსტის `once` და კომენტარის ფორმაში `<input type="hidden" name="once" value="{{ once }}">`. token-ის გაცემა/მოხმარების backend კონტრაქტი შეთანხმდეს UI ცვლილებამდე. UI დამოკიდებულების გარეშე end-to-end token დაცვა დასრულებულად არ გამოცხადდეს.

ქმედებათა მატრიცა და არჩეული idempotency/შეფასების/bulk პოლიტიკა განხორციელებამდე ლუკას პასუხით დაფიქსირდეს. ამ პრომპტში ჩამოთვლილი კითხვები ნებართვა ან საბოლოო გადაწყვეტა არ არის. დამოუკიდებელი ატომური `field_respond` დაცვის მომზადება შეიძლება გაგრძელდეს; სადავო სცენარის დამოკიდებული ლოგიკა პასუხამდე არ განხორციელდეს. აუცილებელი გადაწყვეტილების ან კონტრაქტის არქონისას შესაბამისი ნაწილის სტატუსია **BLOCKED**, არა ვარაუდით PASS.

### განხორციელების მოთხოვნები — დამტკიცებულ მიზნებზე

1. **ატომური optimistic concurrency.** შეთანხმებულ version-მოთხოვნად ქმედებებზე უარყავი გამოტოვებული, ცარიელი, არამთელი ან დაუშვებელი version; არსებული DB მნიშვნელობა ჩუმად არ ჩასვა ფორმის საწყისი version-ის ნაცვლად. შეინარჩუნე ვალიდაციის/როლის შეცდომების უსაფრთხო კონტრაქტი. გადამწყვეტი დაცვა უნდა იყოს DB-ში `UPDATE qc_items … WHERE id=:id AND version=:expected` და version-ის ერთი ატომური გაზრდა, ან lead-ის მიერ ნებადართული ORM versioning; უბრალო „წაიკითხე–შეადარე–ჩაწერე“, მარტო `refresh()`, process-local lock ან SQLite-ზე არაეფექტური `FOR UPDATE` საკმარისი არ არის.
2. **მთელი ქმედების ტრანზაქცია.** CAS/version-ის დაკარგვა → `ConflictError`, არავითარი commit. ცვლილება, მოვლენა, დაკავშირებული codes/people/request/review ჩანაწერები და წერილის ჩანაწერი ერთ წარმატებულ შედეგს უნდა ეკუთვნოდეს. ადრეულმა flush-მა დამარცხებულის მონაცემი ბაზაში არ უნდა დატოვოს. CAS-ის შემდეგ ORM-მა ძველი snapshot-ით `state`, `version`, მომხმარებლის პასუხი ან სხვა ატრიბუტები უკან არ გადაწეროს; successful state-changing მოქმედებაზე version ზუსტად ერთხელ იზრდება. `apply()`-ში შიდა commit-მა route-ის ტრანზაქცია არ დაყოს.
3. **კონფლიქტის ერთიანი შედეგი.** ორი უფლებამოსილი ამზომველი ერთი `expected_version`-ით: გამარჯვებული აფიქსირებს თავის პასუხს, მეორე იღებს `ConflictError`-ის გზას; დაკარგული მცდელობა ახალ version-ზე ავტომატურად არ განმეორდეს როგორც ახალი პასუხი. წაგებულმა შეიძლება `available_actions()`-ში უკვე შეცვლილი მდგომარეობა ნახოს — ასეთ დამტკიცებულ stale-response შემთხვევაშიც დაცული იყოს შეთანხმებული კონფლიქტის განმარტება, არა უბრალოდ ზოგადი role/state უარი. rollback-ის შემდეგ ახალი, სანდო ჩანაწერიდან აჩვენე არსებული „ამ ოქმზე პასუხი უკვე გაგზავნა …“ შეტყობინება; არც დაუმთავრებელი ტრანზაქცია და არც 500.
4. **SQLite და PostgreSQL.** არჩეული სტრატეგია ორივე დიალექტზე სწორი იყოს. SQLite-ის `busy/locked` ან PostgreSQL-ის serialization/deadlock-ის ნებისმიერი შეცდომა ავტომატურად „წარმატებულ კონფლიქტად“ არ მონიშნო. თუ bounded retry საჭიროა, დაასაბუთე და შეინარჩუნე თავდაპირველი expected version/ოპერაციის იდენტობა; მხოლოდ გადამოწმებული stale-write მიათვალე ერთ დამარცხებულ კონკურენტულ მცდელობას. Python mutex-ის ან ტესტის სერიალიზაციის საშუალებით „20/20“-ის მიღება დაუშვებელია.
5. **კომენტარი/შეფასება ვერსიის ზრდის გარეშე.** `comment` და QC `review` შეინარჩუნებს `QcEvent`-ს და არსებულ შესაბამის მონაცემს, მაგრამ არ გაზრდის state/status version-ს. კომენტარის შემდეგ სხვა მომხმარებლის მანამდე გახსნილი უფლებამოსილი ფორმა მხოლოდ კომენტარის გამო არ კონფლიქტდება. ამასთან რეალურად შეცვლილ მდგომარეობაზე ძველი ფორმა არ უნდა იქცეს დაშვებულ ახალ მოქმედებად. `updated_at`-ის ან სხვა metadata-ს ჩაწერამ concurrent state update/version არ გადაფაროს. შეფასების თანაარსებობის ზუსტი შედეგი ღია მატრიცით გადაწყდება.
6. **დუბლიკატის ატომური უარყოფა.** ლუკას მიერ არჩეული key/პერიოდი გამოიყენე იმავე ოქმის/ავტორის შეთანხმებულ ფარგლებში; წინასწარი SELECT ან memory cache მარტო საკმარისი არ არის ორი პარალელური მოთხოვნისთვის. შემოწმება და დუბლიკატის key-ის დაკავება ერთ ტრანზაქციაში იყოს event-ის შექმნასთან. duplicate მოთხოვნამ არ უნდა შექმნას ახალი `QcEvent`, `EmailMessage`, Attachment ან მიტოვებული ფაილი და არ უნდა გაზარდოს version. წარუმატებელი პირველი მცდელობის შემდეგ retry-ის უფლება არჩეული წესით შეინარჩუნე — token მოქმედების ჩავარდნით უნებლიეთ სამუდამოდ არ დაიკარგოს. DB unique constraint ან სხვა საერთო კონტრაქტი თუ სჭირდება, lead-ს მიმართე.
7. **წერილისა და ფაილების თანმიმდევრობა.** `action()`-მა დუბლიკატის შედეგზე მეორედ არ გამოიძახოს `notify.queue()` ისე, რომ დაბრუნებული ძველი event ახალი წერილის საფუძველი გახდეს. წარმატებული ახალი comment-ისთვის ერთჯერადად მომზადდეს ერთი წერილი არსებული to/CC წესით. კონკურენციაში დამარცხებული/rollback მოთხოვნა რეალურ გაგზავნას არ უნდა იწვევდეს; არსებულ commit-მდე `_send()` რისკზე წარმოადგინე ნებადართული ზონის გადაწყვეტა (გაგზავნა მხოლოდ წარმატებული commit-ის შემდეგ ან lead-თან შეთანხმებული მექანიზმი). შეცდომით გაგზავნილი წერილი DB rollback-ით არ ითვლება გასწორებულად. SMTP-ის network crash/retry-ის უნივერსალური exactly-once გარანტია ამ მოთხოვნით ავტომატურად არ მიიღება — outbox/ახალი schema/სრული მიწოდების პოლიტიკა ცალკე შეთანხმების გარეშე არ დაამატო. ფაილების write/rollback-ის გაწმენდაც გადაამოწმე მხოლოდ სატესტო uploads-ში.
8. **Bulk-ის საზღვარი.** `send`-ის სავალდებულო version ვერ შემოივლება `bulk_send()`-ით ან სხვა Python caller-ით. გაფართოებული მოცულობისა და ტრანზაქციის პოლიტიკის დადასტურების შემდეგ უარყოფილი ერთეულის dirty ORM/flush მონაცემი არ დაკომიტდეს სხვა ერთეულის წარმატებასთან ერთად. პარტიის/all-or-nothing ან savepoint შედეგი ტესტში დაემთხვეს ლუკას გადაწყვეტილებას; ამ ორიდან ერთს QA წინასწარ არ ირჩევს. მოქმედ UI bulk კონტროლის აღდგენა არ მოითხოვება.

### უსაფრთხო ტესტირების პროტოკოლი — განხორციელების შემდეგ

**ამ დოკუმენტის მომზადებისას კოდი/ტესტები არ იწერება და არ ეშვება; ქვემოთ შემსრულებლისა და შემდგომი QA-ის პროტოკოლია.**

- ყველა მონაცემი გამოგონილია: ორი მიკუთვნებული ამზომველი, ერთი გაგზავნილი უარყოფითი/რეკომენდაციის ოქმი, მისთვის ნებადართული პასუხები, `example.com`, ყალბი protocol/cadcode და ადგილობრივად გენერირებული სატესტო ფაილები. 4. **B-11 შებრუნებული რეგრესია.** QC-ის ნებადართული კომენტარი `notify=on`: ერთი token/შეთანხმებული იგივე ტექსტი ორჯერ თანმიმდევრულად → ერთი `comment`, ერთი EmailMessage და ერთი სატესტო send მცდელობა, როცა ტრანსპორტი დამჭერით აქტიურია; ჩვეულებრივ preview რეჟიმშიც მხოლოდ ერთი ჩანაწერი. იგივე შემთხვევა ორი პარალელური POST-ითაც გაიმეორე. სხვა ოქმი, სხვა ავტორი, შეცვლილი ტექსტი, `notify` არჩევანი, 60 წმ საზღვარი ან ახალი token — შედეგი მხოლოდ დამტკიცებული პოლიტიკის მიხედვით. დროითი ტესტები კონტროლირებადი clock-ით შეასრულე, რეალურად 60-წამიანი ძილი არ არის საჭირო.

8. **Bulk (პასუხის შემდეგ).** სწორი ოქმი + წარუმატებელი ოქმი + კონფლიქტური ოქმი; მეორე/მესამე მოქმედება ჩააგდე ცვლილების ან flush-ის შემდეგ. მესამე სესიით გადაამოწმე ყველა ველი/კოდი/მოვლენა/version და შედეგის მთვლელები. all-or-nothing პოლიტიკისას ყველა უცვლელია; ერთეულების დამოუკიდებელი პოლიტიკისას მხოლოდ სრულად წარმატებული ერთეულები ინახება. სავალდებულო version-ის გარეშე bulk-მ ვერ უნდა გააგზავნოს. ეს ნაწილი მოცულობის დადასტურების გარეშე არ სრულდება.
