   `version` ფორმაში **სავალდებულოა** მდგომარეობის შემცვლელ ქმედებებზე (T-010, S-09).

   B-12: კომენტარი და QC მენეჯერის შეფასება `version`-ს **არ** ზრდის (კონფლიქტი მხოლოდ მდგომარეობის / სტატუსის ცვლილებაზე).

## 2. პრომპტი შემსრულებლისთვის — qa (Codex)

> ბრიფს არ ცვლის — მხოლოდ „როგორ“-ს ამატებს. დასრულების პირობა ნაწილი 1-იდან სიტყვასიტყვით.

### კონტექსტი და სტატუსი

**პრომპტი განახლებულია ლუკას სავალდებულო გადაწყვეტილებებით, 2026-10-27.** შენ ხარ backend. T-019 არის P0: ერთ ოქმზე ერთ საწყის ვერსიაზე კონკურენტული ველის პასუხებიდან მხოლოდ პირველი წარმატებული ჩაწერა უნდა ჩაითვალოს; კომენტარის განმეორებით გაგზავნამ მეორე მოვლენა/წერილი არ უნდა შექმნას. წყაროა ნაწილი 1, `docs/OPEN_QUESTIONS.md` და `docs/reports/STAGE-1-SUMMARY.md` P0-2; რიგი — T-015 → T-019 → T-011. Backend Claude-ს არსებული წინასწარი ანალიზი გამოიყენე საწყისად და გადაამოწმე კოდთან. ქვემოთ მოცემული ხუთი გადაწყვეტილება სავალდებულოა და ცვლის ადრინდელ ალტერნატივებს; token-ის ნაცვლად 60-წამიანი შედარება, ORM `version_id_col` ან bulk ტრანზაქციის შენარჩუნება აღარ განიხილება.

**განხორციელების წინაპირობა:** ლუკას ცნობით განახლებულ main-ში `app/models.py`-ს უკვე დაემატა `FormToken`. Backend განხორციელებას იწყებს მხოლოდ განახლებული main-ის მიღებისა და იქ არსებული `FormToken` კონტრაქტის წაკითხვის შემდეგ. ეს პრომპტი main-ის ფაქტობრივი სინქრონიზაციის მტკიცებულება არ არის: ამ დოკუმენტაციის განახლებისას fetch/pull/merge არ შესრულდება. Backend-მა თავის ბრენჩში გამოიყენოს lead-ის მიღებული კონტრაქტი, `models.py` თვითონ არ შეცვალოს.

### წასაკითხი წყაროები და მიმდინარე პრობლემა

წაიკითხე `AGENTS.md`, `docs/team/roles/backend.md`, `docs/team/SALOME.md`, `DESIGN.md`, ამ დოკუმენტის ნაწილები 1–2 და `docs/TASKS.md`. დიზაინი ამ ამოცანაში არ იცვლება. სამუშაო ბრენჩია `backend/T-019-concurrency`, შეთანხმებული T-015-ის საფუძველზე; არსებული სამუშაო არ გადაწერო და main-ში არ ჩაწერო.

- `docs/reports/T-007-backend-audit.md`, **B-11**: ერთი კომენტარის ფორმის `notify=on`-ით ორჯერ გაგზავნა ქმნის ორ `comment` მოვლენასა და ორ მეილს. აუდიტის ალტერნატივებიდან ლუკამ აირჩია ერთჯერადი `once` token და `FormToken`-ით დაცვა; ტექსტის/ადრესატის 60-წამიანი შედარება არ გამოიყენება.
- იქვე **B-12**, ფრაგმენტი `test_b_comment_bumps_version`: კომენტარის შემდეგ ოპერატორის ძველი `version`-ით `edit` ცრუ კონფლიქტს იღებს. T-019 ამტკიცებს, რომ `comment` და QC `review` ვერსიას არ ზრდის; ეს არ ნიშნავს მათი მოვლენების/აუდიტის გაუქმებას.
- `docs/reports/T-009-e2e.md`, **E-06**: ნამდვილი კონკურენტული ორი პასუხი ორივე ინახება. `tests/test_workflow.py:test_second_surveyor_gets_conflict` თანმიმდევრული შემთხვევაა და ამ რისკს მარტო ვერ ამტკიცებს. T-010-ის **S-09**-ის კავშირიც შეამოწმე — ფორმის `version` სავალდებულო არაა.
- `app/workflow.py:apply()`: `form.get("version")` მხოლოდ არსებობისას შედარდება წაკითხულ `item.version`-ს; ეს Python შედარება არ არის ატომური. `_event()`, `_set_codes()`, `_set_surveyors()` და `save_files()` გზაზე flush-ებია, ბოლოს კი ყველა ქმედებაზე `item.version += 1` ხდება. ტრანზაქციის დაცვა ყველა ამ გვერდით ეფექტს უნდა მოიცავდეს.
- `app/routes/items.py:action()`: `apply()` → `notify.queue()` → `db.commit()`; `ConflictError`/`WorkflowError`-ზე rollback და redirect. დღეს `notify.queue()` კონფიგურირებული SMTP-ისას commit-მდე `_send()`-საც იძახებს. ტრანზაქციის rollback უკვე გაგზავნილ წერილს ვერ დააბრუნებს.
- `app/routes/qc.py:bulk_send()`: `send`-ს `version`-ის გარეშე იძახებს; `WorkflowError`-ს იჭერს და ციკლს აგრძელებს; ბოლოს ერთი commit-ია. ადრინდელი flush-ების გამო ნაწილობრივი ცვლილების რისკზე ლუკას გადაწყვეტაა route-ის და მისი ძველი ტესტების წაშლა T-019-ში. UI-დან ღილაკის მოცილება მარტო endpoint-ს არ აუქმებს.

| **კომენტარის დუბლიკატი** | მხოლოდ ერთჯერადი `once` token: ბარათის კონტექსტში `secrets.token_urlsafe(24)`; POST-ზე `FormToken`-ის მოხმარება და კომენტარის შექმნა ერთ DB ტრანზაქციაში. გამოყენებული token → არავითარი ახალი მოვლენა/email, შეტყობინება **„კომენტარი უკვე დამატებულია“**. token-ის გარეშე → **„განაახლეთ გვერდი“**. ტექსტის 60-წამიანი შედარება არ გამოიყენება; იგივე token შეცვლილი ტექსტით/notify-ითაც უკვე გამოყენებულია, განსხვავებული token-ების same-text კომენტარები დროით არ იფილტრება |
| **მხოლოდ ფოტოს შემცველი კომენტარი** | დასაშვებია არსებული QC ატვირთვის უფლებებით; იყენებს იმავე `once`/`FormToken` დაცვას. ცარიელი ტექსტის, ფაილის სახელის ან hash-ის მიხედვით დამატებითი dedup წესი არ შემოიღო |
| **მდგომარეობის ცვლილება / QC შეფასება** | მდგომარეობის ცვლილებებზე პირველი წარმატებული ოპერაცია იმარჯვებს. `review`-ზე **ბოლო წარმატებული ჩაწერა იმარჯვებს**, ორივე წარმატებული შეფასება ისტორიაში ჩანს და version უცვლელია. პირველი `QcReview`-ის ერთდროული შექმნის `IntegrityError` დამუშავდეს უკვე შექმნილი ჩანაწერის განახლებით, არა HTTP 500-ით ან მეორე შეფასების დაკარგვით |
| **`/qc/bulk-send`** | T-019-ში route და მისი ძველი ტესტები **წაიშალოს**. `routes/qc.py`-ში ეს მხოლოდ ამ route-ისთვის დაშვებული გამონაკლისია. all-or-nothing/savepoint პარტიის ახალი ლოგიკა აღარ განხორციელდება |

ეს ხუთი საკითხი აღარ არის ღია. განხორციელების წინაპირობაა განახლებული main-ის მიღება და `FormToken`-ის არსებული ველების/შეზღუდვების გამოყენება; მიღებამდე Backend განხორციელება **BLOCKED**-ია. სხვა გუნდის დარჩენილი დამოკიდებულებაა T-016-ის hidden `once` ველი. ახალ, ამ გადაწყვეტილებებით დაუფარავ საერთო კონტრაქტის ხარვეზზე მიმართე lead-ს; მიღებული გადაწყვეტილებები თავიდან დასადასტურებლად არ დააბრუნო.

### განხორციელების მოთხოვნები — დამტკიცებულ მიზნებზე

1. **ატომური optimistic concurrency.** `apply()`-ის ყველა მოქმედებაზე, გარდა `comment`/`review`-სა, უარყავი გამოტოვებული, ცარიელი, არამთელი ან დაუშვებელი version; არსებული DB მნიშვნელობა ჩუმად არ ჩასვა ფორმის საწყისი version-ის ნაცვლად. შეინარჩუნე ვალიდაციის/როლის შეცდომების უსაფრთხო კონტრაქტი. გადამწყვეტი დაცვა არის ზუსტად DB-ში `UPDATE qc_items SET version = version + 1 WHERE id = :id AND version = :v`; rowcount 0 → `ConflictError`. ORM `version_id_col` არ გამოიყენო და ბოლოს `item.version += 1` აღარ დაამატო. უბრალო „წაიკითხე–შეადარე–ჩაწერე“, მარტო `refresh()`, process-local lock ან SQLite-ზე არაეფექტური `FOR UPDATE` საკმარისი არ არის.
2. **მთელი ქმედების ტრანზაქცია.** CAS/version-ის დაკარგვა → `ConflictError`, არავითარი commit. ცვლილება, მოვლენა, დაკავშირებული codes/people/request/review ჩანაწერები და წერილის ჩანაწერი ერთ წარმატებულ შედეგს უნდა ეკუთვნოდეს. ადრეულმა flush-მა დამარცხებულის მონაცემი ბაზაში არ უნდა დატოვოს. CAS-ის შემდეგ ORM-მა ძველი snapshot-ით `state`, `version`, მომხმარებლის პასუხი ან სხვა ატრიბუტები უკან არ გადაწეროს; successful state-changing მოქმედებაზე version ზუსტად ერთხელ იზრდება. `apply()`-ში შიდა commit-მა route-ის ტრანზაქცია არ დაყოს.
3. **კონფლიქტის ერთიანი შედეგი.** ორი უფლებამოსილი ამზომველი ერთი `expected_version`-ით: გამარჯვებული აფიქსირებს თავის პასუხს, მეორე იღებს `ConflictError`-ის გზას; დაკარგული მცდელობა ახალ version-ზე ავტომატურად არ განმეორდეს როგორც ახალი პასუხი. წაგებულმა შეიძლება `available_actions()`-ში უკვე შეცვლილი მდგომარეობა ნახოს — ასეთ დამტკიცებულ stale-response შემთხვევაშიც დაცული იყოს შეთანხმებული კონფლიქტის განმარტება, არა უბრალოდ ზოგადი role/state უარი. rollback-ის შემდეგ ახალი, სანდო ჩანაწერიდან აჩვენე არსებული „ამ ოქმზე პასუხი უკვე გაგზავნა …“ შეტყობინება; არც დაუმთავრებელი ტრანზაქცია და არც 500.
4. **SQLite და PostgreSQL.** არჩეული სტრატეგია ორივე დიალექტზე სწორი იყოს. SQLite-ის `busy/locked` ან PostgreSQL-ის serialization/deadlock-ის ნებისმიერი შეცდომა ავტომატურად „წარმატებულ კონფლიქტად“ არ მონიშნო. თუ bounded retry საჭიროა, დაასაბუთე და შეინარჩუნე თავდაპირველი expected version/ოპერაციის იდენტობა; მხოლოდ გადამოწმებული stale-write მიათვალე ერთ დამარცხებულ კონკურენტულ მცდელობას. Python mutex-ის ან ტესტის სერიალიზაციის საშუალებით „20/20“-ის მიღება დაუშვებელია.
5. **კომენტარი/შეფასება ვერსიის ზრდის გარეშე.** `comment` და QC `review` შეინარჩუნებს `QcEvent`-ს და არსებულ შესაბამის მონაცემს, მაგრამ version-ს არც მოითხოვს და არც გაზრდის. კომენტარის შემდეგ სხვა მომხმარებლის მანამდე გახსნილი უფლებამოსილი ფორმა მხოლოდ კომენტარის გამო არ კონფლიქტდება. ამასთან რეალურად შეცვლილ მდგომარეობაზე ძველი ფორმა არ უნდა იქცეს დაშვებულ ახალ მოქმედებად. `updated_at`-ის ან სხვა metadata-ს ჩაწერამ concurrent state update/version არ გადაფაროს. პარალელურ review-ზე ბოლო წარმატებული ჩაწერა ინახება `QcReview`-ში, ორივე `qc_reviewed` ისტორია რჩება. პირველადი insert-ის შეჯახების `IntegrityError` დაამუშავე ტრანზაქციის უსაფრთხო საზღვარში უკვე არსებული ჩანაწერის განახლებით; შეცდომამ წარმატებული მეორე შეფასება/ისტორია არ გააქროს და session failed მდგომარეობაში არ დატოვოს. შეფასების დამარცხებულ insert მცდელობას დამატებითი/მესამე ისტორია არ მიეწეროს.
6. **ერთჯერადი token-ის ატომური მოხმარება.** ბარათის context-ში `once = secrets.token_urlsafe(24)`. POST `comment`-ზე მიღებული `once` და განახლებული main-ის `FormToken` გამოიყენე; FormToken-ის ჩაწერა/მოხმარება, კომენტარის მოვლენა და შესაბამისი DB გვერდითი ეფექტები ერთ ტრანზაქციაში იყოს. არსებული კონტრაქტის unique/ატომური გარანტია დაიცავი — წინასწარი SELECT ან memory cache მარტო საკმარისი არ არის. გამოყენებული token-ის შემთხვევაში route-მ აჩვენოს **„კომენტარი უკვე დამატებულია“**, ხოლო token-ის გარეშე — **„განაახლეთ გვერდი“**; ორივე შემთხვევაში ახალი `QcEvent`, `EmailMessage`, Attachment ან მიტოვებული ფაილი არ შეიქმნას და version არ გაიზარდოს. duplicate შედეგი route-მ გაარჩიოს ახალი მოვლენისგან. პირველადი ცდის rollback-მა token-ის მოხმარებაც უნდა გააუქმოს, რათა გამართული retry შესაძლებელი დარჩეს. იგივე კონტრაქტი ვრცელდება მხოლოდ ფოტოს შემცველ კომენტარზე. 60-წამიანი ტექსტის/ადრესატის შედარება და ფაილის hash-ზე ახალი წესი არ გამოიყენო.
7. **წერილისა და ფაილების თანმიმდევრობა.** `action()`-მა დუბლიკატის შედეგზე მეორედ არ გამოიძახოს `notify.queue()` ისე, რომ დაბრუნებული ძველი event ახალი წერილის საფუძველი გახდეს. წარმატებული ახალი comment-ისთვის ერთჯერადად მომზადდეს ერთი წერილი არსებული to/CC წესით. კონკურენციაში დამარცხებული/rollback მოთხოვნა რეალურ გაგზავნას არ უნდა იწვევდეს; არსებულ commit-მდე `_send()` რისკზე წარმოადგინე ნებადართული ზონის გადაწყვეტა (გაგზავნა მხოლოდ წარმატებული commit-ის შემდეგ ან lead-თან შეთანხმებული მექანიზმი). შეცდომით გაგზავნილი წერილი DB rollback-ით არ ითვლება გასწორებულად. SMTP-ის network crash/retry-ის უნივერსალური exactly-once გარანტია ამ მოთხოვნით ავტომატურად არ მიიღება — outbox/ახალი schema/სრული მიწოდების პოლიტიკა ცალკე შეთანხმების გარეშე არ დაამატო. ფაილების write/rollback-ის გაწმენდაც გადაამოწმე მხოლოდ სატესტო uploads-ში.
8. **Bulk route-ის წაშლა.** წაშალე `/qc/bulk-send` route `app/routes/qc.py`-დან და მისი ძველი ტესტები; მხოლოდ ამ route-ის გამოუყენებელი import/helper გაწმინდე, დანარჩენ route-ებს არ შეეხო. სხვა საერთო ტესტის ნებადართული send/version assertions შეინარჩუნე. ახალი პარტიული ტრანზაქცია, savepoint გზა ან UI bulk კონტროლის აღდგენა არ დაამატო. ახალ რეგრესიულ შემოწმებაში POST `/qc/bulk-send` აღარ უნდა იყოს მოქმედი route (404) და DB მონაცემს არ უნდა ცვლიდეს; OpenAPI-შიც route აღარ იყოს.

### უსაფრთხო ტესტირების პროტოკოლი — განხორციელების შემდეგ

**ამ დოკუმენტის მომზადებისას კოდი/ტესტები არ იწერება და არ ეშვება; ქვემოთ შემსრულებლისა და შემდგომი QA-ის პროტოკოლია.**

- Python-ის/აპლიკაციის გაშვებამდე `QCP_AGENT=1`. ტესტებისთვის გამოიყენე სრულიად ახალი დროებითი, ფაილური SQLite ბაზა (WAL/შესაბამისი timeout); ძირითადი fixtures — `tests/conftest.py`, მაგრამ thread-ებს საკუთარი SQLAlchemy Session/კავშირები ჰქონდეს. საერთო live demo ან `:memory:` singleton კავშირი პარალელური ტესტისთვის არ გამოიყენო. იმპორტამდე გადაამოწმე რომ სატესტო DB/UPLOAD/DISTRIBUTOR მისამართები მხოლოდ ახალ დემო/დროებით სივრცეშია; კონფიგურაციის საიდუმლო მნიშვნელობები არ დაბეჭდო და საიდუმლო ფაილები არ წაიკითხო.

1. **20 დამოუკიდებელი რბოლა.** ყოველ რაუნდში თავიდან მოამზადე შესაბამისი ოქმის საწყისი მდგომარეობა/version; fixture ცვლილებები commit-დეს worker-ების დაწყებამდე. ორი სხვადასხვა ავტორიზებული HTTP სესია, ორი thread, ორი დამოუკიდებელი DB Session/კავშირი; ერთი `expected_version`, დაწყების barrier/event და თითოეული futures-ის timeout. ორივე POST რეალურად გადაიფაროს; დაამტკიცე, რომ ორივე ხედავდა ერთ საწყის ვერსიას, საჭიროებისას მხოლოდ ტესტში გამოყენებული სინქრონიზაციით CAS-მდე. worker-ებში საერთო Session/ORM ობიექტი ან ტესტის lock-ით რიგრიგობით commit არ გამოიყენო. write lock-ის აღების შემდეგ ერთმანეთის მომლოდინე barrier deadlock-ს ნუ შექმნი; `sleep` მარტო race-ის მტკიცებულება არ არის.

3. **ვერსიის ვალიდაცია.** `apply()`-ის ყველა მოქმედებაზე, გარდა `comment`/`review`-სა, პარამეტრიზებული HTTP და service შემოწმებები: აკლია, ცარიელია, ტექსტია, არამთელია, ძველია, მიმდინარეა. `save_review`, `edit`, request-ის ქმედებები, `reassign`/`assign_manager` არ გამოტოვო მხოლოდ იმიტომ, რომ state შეიძლება უცვლელი იყოს. `form`-ის საჭირო სხვა ველები სწორად შეავსე, რათა version-ის უარი სხვა ვალიდაციამ არ დაფაროს. stale/არასწორ მოთხოვნაზე DB გვერდითი ეფექტი ნულია; წარმატებულზე version ზუსტად `v+1`-ია, არა `v+2`. `comment`/`review` version-ის გარეშე და ძველი version-ითაც არ იღებს version კონფლიქტს; comment-ს ამ დროს მაინც სწორი `once` სჭირდება. დაუშვებელი როლი, სხვისი/გაუგზავნელი ოქმი და უცხო Origin კვლავ უარყოფილია.
4. **B-11 შებრუნებული რეგრესია.** QC-ის ნებადართული კომენტარი `notify=on`: **ერთი `once` token** ორჯერ თანმიმდევრულად → ერთი `comment`, ერთი EmailMessage და ერთი სატესტო send მცდელობა, როცა ტრანსპორტი დამჭერით აქტიურია; ჩვეულებრივ preview რეჟიმშიც მხოლოდ ერთი ჩანაწერი. იგივე შემთხვევა ორი პარალელური POST-ითაც გაიმეორე: FormToken ერთჯერადად მოიხმარება, მეორე პასუხში **„კომენტარი უკვე დამატებულია“**, მოვლენა/email აღარ ემატება. token-ის გარეშე — **„განაახლეთ გვერდი“**, DB გვერდითი ეფექტი ნულია. გამოყენებული token შეცვლილი ტექსტით ან notify-ითაც არ ქმნის ახალ მოვლენას/წერილს; ორი ახალი განსხვავებული token-ით იგივე ტექსტი ხელოვნურად 60-წამიანი წესით არ დაიბლოკოს. GET context-ის `once` მომზადება და არსებული `FormToken` კონტრაქტიც შემოწმდეს; T-016 hidden ველის მიუღებლობა ცალკე დამოკიდებულებად აღირიცხოს.
5. **B-12 შებრუნებული რეგრესია.** ოპერატორის ღია `edit` ფორმიდან აიღე `v`; სხვა ნებადართული მომხმარებლის `comment`-ის სწორი token-ით commit-ის შემდეგ version ისევ `v` არის და ოპერატორის იმავე `v`-იანი ნებადართული edit კომენტარის გამო არ იბლოკება. წარმატებული edit შემდეგ version `v+1`-ია. ასევე `review`-ზე version უცვლელი რჩება. განსხვავება: ყველა სხვა რეალურმა `apply()` მოქმედებამ stale ფორმის დაცვა უნდა აამუშაოს.
