## 1. ბრიფი — lead

**მიზანი:** QA-მ (T-028, `qa/T-028-on-t019` / `283d648`) დაადასტურა, რომ ოქმის პასუხისმგებელ საველე მენეჯერად და წერილის ადრესატად შეიძლება
მოხვდეს QC-ის მომხმარებელი: `assign_manager` სერვერზე როლს არ ამოწმებს (მხოლოდ ფორმის ჩამონათვალი იცავს), `notify.recipients()` ადრესატს
მიკუთვნებიდან იღებს როლის შემოწმების გარეშე. ეს არღვევს კონფიდენციალურობის წესს (T-015) და უსაფრთხოების ჩეკლისტს („ქმედება სერვერზე მოწმდება“).
ლუკას გადაწყვეტილება — `docs/OPEN_QUESTIONS.md`, „საველე მენეჯერი — ვინ შეიძლება იყოს“ (2026-10-27).

**წესი:** „დასაშვები საველე მენეჯერი“ = `user.active` **და** `user.has_role(D.FIELD_MANAGER)`. ორმაგი როლი (საველე მენეჯერი + QC / ადმინი) — დასაშვებია.

**შედის:**
1. `workflow.apply()` → `assign_manager`: `manager_id` დასაშვები საველე მენეჯერი არ არის → `WorkflowError("აირჩიეთ საველე მენეჯერი.")`, ცვლილება არ შედის.
   (ფორმის `manager_options` უკვე ასეა — ახლა სერვერიც.) ერთი დამხმარე ფუნქცია, მაგ. `is_field_manager(user)` — ერთ ადგილას, ორივე წერტილისთვის.
2. `notify.recipients()`: To და CC — მხოლოდ დასაშვები საველე მენეჯერები. პასუხისმგებელი დასაშვები არ არის → To ხდება პირველი დასაშვები CC (არსებული ლოგიკა);
   არცერთი → `(None, [])`.
3. `notify.queue()` — დამატებითი დაცვა: To დასაშვები არ არის → `None` (წერილი არ იქმნება), იმ შემთხვევისთვისაც, თუ ვინმე `recipients()`-ს გვერდს აუვლის.
4. დასაშვები ადრესატი არ არის → მოქმედება **სრულდება**, `EmailMessage` არ იქმნება; ბარათზე შეტყობინებას ემატება
   „✉ წერილი არ შეიქმნა — ოქმს საველე მენეჯერი არ ჰყავს.“ (`routes/items.py`, `notice`). სერვერის ლოგში — `warning` ოქმის `id`-ით
   (**სახელის გარეშე**). ცალკე აუდიტის ცხრილი არ სჭირდება — მოქმედება `QcEvent`-ში ისედაც იწერება.
5. ძველი არასწორი მიკუთვნებები — `scripts/check_field_managers.py` (ახალი, **მხოლოდ კითხვა**): ჩამოთვლის ოქმებს, სადაც `field_manager_id` ან
   მენეჯერის `ItemPerson` დასაშვები საველე მენეჯერი არ არის — ოქმის# და რაოდენობა, **სახელების გარეშე**. ბაზაში არაფერს წერს.
   რეალურ ბაზაზე უშვებს **მხოლოდ ლუკა** (აგენტები — დემოზე); გასწორება — ბარათზე „მენეჯერის მიწერა“-თი (QC მენეჯერი / ადმინი).
6. ტესტები: QA-ის 4 ჩავარდნილი ტესტი (`283d648`) qa გადააქვს ამ ბრენჩზე; ორმაგი როლის შემთხვევა — ლუკას წესით **დასაშვებია**
   (ტესტი: „To-ს ყოველთვის აქვს აქტიური საველე მენეჯერის როლი“, არა „To-ს არასოდეს აქვს QC როლი“).

**არ შედის:** შაბლონები; როლების ადმინისტრირება; ძველი მონაცემის ავტომატური გასწორება; `sender_name` (T-015) — უცვლელი
(ახლა ყველა ადრესატი საველე მენეჯერია → გამომგზავნი ყოველთვის ანონიმურია).

**ფაილები (ზონა):** `app/workflow.py`, `app/services/notify.py`, `app/routes/items.py` (`notice`), `scripts/check_field_managers.py` (ახალი), ტესტები.

**დასრულების პირობა** (ტესტირებადი):
1. `assign_manager` QC-ის მომხმარებლით / როლის გარეშე / არააქტიური მომხმარებლით → უარი, `field_manager_id` უცვლელი; ორმაგი როლით და ჩვეულებრივი საველე მენეჯრით → მუშაობს.
2. `recipients()` / `queue()`: To და CC-ში არასოდეს არის მომხმარებელი აქტიური საველე მენეჯერის როლის გარეშე; ასეთი მხოლოდ რომ იყოს → წერილი არ იქმნება,
   მოქმედება სრულდება, შეტყობინება ჩანს. HTTP გზითაც (ბარათის ფორმა, „✉ მენეჯერს მეილითაც“).
3. `check_field_managers.py` დემო ბაზაზე მუშაობს, არაფერს წერს (ბაზის ფაილის `mtime` უცვლელია), სახელს არ ბეჭდავს.
4. `pytest -q` გადის (QA-ის 4 ტესტის ჩათვლით); `smoke_pages.py` დემო ბაზაზე — 0 შეცდომა.

**ჩაბარებისას შევამოწმებ:** წესი ერთ ფუნქციაშია და სამივე ადგილი მას იყენებს; ლოგში და სკრიპტის გამოტანაში სახელი არ არის.
