## 1. ბრიფი — lead

**მიზანი:** T-007-ის კითხვებზე ლუკამ უპასუხა (`docs/OPEN_QUESTIONS.md`, 2026-10-27, T-007 Q-01 – Q-05). კოდი ამ წესებს უნდა მიჰყვეს;
აქვე იხურება B-02, B-03, B-04 (`docs/reports/T-007-backend-audit.md`).

**შედის:**
1. **QC მენეჯერის გადაწყვეტილება (Q-01, B-04):** „ორივე მართალია“ → დადებითი, `qc_error = False`; „ველი მართალია“ → დადებითი, `qc_error = True`.
   ხელახლა გახსნისას / სტატუსის შეცვლისას (`_reopen_to_field`, `change_verdict`, მოთხოვნის დადასტურება) — `qc_error`, `both_right`, `qcm_decision`,
   `corrected_confirmed`, `confirmed_at` სუფთავდება; ძველი მნიშვნელობა — მოვლენის `data.before`-ში.
2. **ველის ხილვადობა (Q-02):** ველი ხედავს ყველა ოქმს, რომელზეც კითხვა მიიღო (პირველი გაგზავნა არ იყო დადებითი — მაგ. `original_verdict != positive`),
   დადებითად დასრულებულსაც; თავიდანვე დადებითი — არა. `scope.field_visible()` და `can_view` ამის მიხედვით.
   საბოლოოდ დადასტურებული (`closed`) — ველის მთავარ „გასავლელ“ სიაში არა; ფილტრით / ძებნით (T-011) — კი.
3. **ველის პასუხები (Q-03):** უარყოფითი — „შესწორდა“, „არ ვეთანხმები“; რეკომენდაცია — სამივე (lead-მა `D.DEFAULT_ALLOWED_RESPONSES` უკვე შეცვალა);
   დაზუსტება — მხოლოდ `R_ANSWER` (კომენტარი სავალდებულო). რეკომენდაციაზე „შესწორდა“ → QC-ის გადამოწმება, დადასტურებისას — „გათვალისწინებული“.
   **ბაზაში შენახული** `Setting("allowed_responses")` — ერთჯერადი განახლება გაშვებისას, თუ ძველ ნაგულისხმევს ემთხვევა (ადმინის ხელით შეცვლილს არ ეხება).
   ძველი ცხრილის იმპორტი (`legacy_import.derive_state`, T-007 Q-03): დაზუსტება + ველის პასუხი → QC-სთან გადასაწყვეტად (`awaiting_qc`).
4. **პასუხის დრო (Q-04):** `stats`-ში — პირველი გაგზავნა (`first_sent_at`) → ველის **პირველი** პასუხი (პირველი `field_responded` მოვლენა).
   მეტრიკის განმარტება — `docs/ARCHITECTURE.md` §7-ისთვის lead-ს მიაწოდე (commit-ის აღწერაში).
5. **სტატუსის შეცვლის მოთხოვნა (Q-05, B-02, B-03):** ღია მოთხოვნისას ოქმი ველს **არ უჩანს** (სიები, ბარათი, API, მთავარი, სტატისტიკა, მეილი — `scope`-ში ერთი პირობით);
   დავის დროს (`awaiting_manager`, `awaiting_qcm`, `returned_to_manager`) მოთხოვნა ვერ შეიქმნება; QC მენეჯერის `change_verdict` ღია მოთხოვნას აუქმებს
   (`rejected`, მიზეზი „მოძველდა — სტატუსი QC მენეჯერმა შეცვალა“); დადასტურებისას `req.from_verdict == item.verdict`, სხვა შემთხვევაში უარი.

**არ შედის:** შაბლონები (ღილაკების დამალვა — ui, საჭიროებისას „სხვა როლებისგან სჭირდება“); ერთდროული ჩაწერა — T-019; ფილტრები — T-011.

**ფაილები (ზონა):** `app/workflow.py`, `app/scope.py`, `app/services/stats.py`, `app/services/legacy_import.py`, `app/services/seed.py`, `app/main.py` (ერთჯერადი განახლება),
`tests/test_rules.py` (ახალი — ნებადართული გამონაკლისი).

**კონტრაქტი (backend ↔ ui):** არ იცვლება (`available_actions` უკვე განსაზღვრავს ღილაკებს).

**დასრულების პირობა** (ტესტირებადი):
1. „ორივე მართალია“ → `qc_error False`; „ველი მართალია“ → `True`; შემდეგ `change_verdict` → ნიშნები გასუფთავდა, `data.before`-ში შენახულია (B-04 ფრაგმენტი — შებრუნებული).
2. დაზუსტება → პასუხი → „დადებითი“ → ამზომველი ბარათს ხედავს (200), „გასავლელში“ არ არის, `/field?state=closed` / ძებნით — ჩანს; თავიდანვე დადებითი → 404.
3. რეკომენდაციაზე „შესწორდა“ → `awaiting_qc` → დადასტურება → `acknowledged`; უარყოფითზე „გავითვალისწინებთ“ → უარი; დაზუსტებაზე სტატუსი → უარი.
4. პასუხის დრო = პირველი გაგზავნა → პირველი პასუხი (ორწრიანი ოქმით).
5. ღია მოთხოვნა → ამზომველი `/items/{id}` → 404 და სიაში არ ჩანს; QC მენეჯერის უარის შემდეგ — ისევ ჩანს. დავის დროს მოთხოვნა → უარი;
   `change_verdict` → მოთხოვნა `rejected` (B-02, B-03 ფრაგმენტები — შებრუნებული).
6. `pytest -q` გადის; `smoke_pages.py` დემო ბაზაზე — 0 შეცდომა.

**ჩაბარებისას შევამოწმებ:** წესები = `OPEN_QUESTIONS.md`-ის ტექსტი; ველს ღია მოთხოვნიანი ოქმი არსად (API-შიც).
